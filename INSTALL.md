# Установка conveyor — пошагово

Плагин ставится в **GigaCode CLI** (как расширение) и в **Claude Code** (как
плагин). Ниже — по шагам для каждой среды.

Предварительно нужно:
- **Node.js ≥ 14** — проверьте: `node --version`;
- **git** в PATH — проверьте: `git --version`;
- установленный **GigaCode CLI** (`gigacode --version`) — для установки в GigaCode;
- доступы к репозиториям команды (системный анализ, фронтенд, бэкенд,
  автотесты; бэкенд обычно разложен на `core`, `api`, `common`, `config` —
  это отдельные репозитории): их рабочие копии вы клонируете сами —
  **плагин не клонирует**.

---

## A. GigaCode CLI

### Шаг 1. Получить исходники плагина
Скопируйте/склонируйте каталог плагина к себе и перейдите в него:
```
cd путь/к/conveyor        # каталог, где лежат core/, adapters/, scripts/
```

### Шаг 2. Собрать дистрибутив
```
node scripts/build.mjs
```
Появится `dist/gigacode/` — готовое расширение (манифест
`gigacode-extension.json`, `QWEN.md`, `commands/conveyor/*`, вложенный `core/`).

### Шаг 3. (Опционально) Прогнать самопроверку
```
node scripts/check.mjs
```
Должно закончиться строкой «Все проверки пройдены».

### Шаг 4. Установить расширение штатной командой GigaCode
```
gigacode extensions install dist/gigacode
```
GigaCode покажет security-предупреждение («Extensions may introduce
unexpected behavior») — подтвердите вводом `Y`.
Команда сама скопирует файлы в `~/.gigacode/extensions/conveyor/` и
ЗАРЕГИСТРИРУЕТ расширение в реестре.

> Не копируйте вручную (`cp -r`) — ручное копирование не регистрирует
> расширение, и в списке команд оно не появится.

### Шаг 5. Проверить, что расширение встало
```
gigacode extensions list
```
Ожидаемый вывод: `conveyor (<версия>)`, `Enabled (User): true`,
`Enabled (Workspace): true` и 8 команд:
`/conveyor:setup`, `/conveyor:intent`, `/conveyor:create-specification`,
`/conveyor:create-plan`, `/conveyor:implement-plan`,
`/conveyor:create-autotest-plan`, `/conveyor:implement-auto-test`,
`/conveyor:task-status`.

Каталог установки команды определяют сами: шаг «Корень расширения» в начале
каждой команды ищет `~/.gigacode/extensions/conveyor` и проверяет, что там
лежит ядро плагина. Не нашёл — этап останавливается и спрашивает каталог у
вас, а не гадает.

### Шаг 6. Запустить GigaCode в рабочем репозитории и инициализировать его
Рабочий репозиторий (workspace) — отдельный git-репозиторий команды с
конфигурацией и артефактами задач. Если он у команды уже есть — склонируйте его
и переходите к шагу 7: `settings.json` приезжает вместе с ним, создавать нечего.

Если рабочего репозитория ещё нет (это делает тимлид один раз):
```
gigacode
/conveyor:setup
```
`/conveyor:setup` спросит `taskPrefix` и создаст в текущем каталоге
`settings.json`, `.env.example`, `tasks/FE`, `tasks/BE`, `intents/`, `repos/`,
`.gitignore` (в нём `repos/` и `.env`). `settings.json` нужно **закоммитить**:
он одинаков у всей команды. Файл `.env` не создаётся — он не обязателен.

### Шаг 7. Склонировать репозитории в `repos/`
Плагин не клонирует: рабочие копии заводит каждый разработчик сам — своими
доступами (ssh-ключи, подмодули, LFS). Пути берутся из `settings.json`
(`repos.<ключ>.link`, по умолчанию — как ниже) и резолвятся ОТНОСИТЕЛЬНО корня
рабочего репозитория:

```
git clone <url-анализа>        repos/system-analysis
git clone <url-фронтенда>      repos/frontend
git clone <url-backend-core>   repos/backend/core
git clone <url-backend-api>    repos/backend/api
git clone <url-backend-common> repos/backend/common
git clone <url-backend-config> repos/backend/config
git clone <url-автотестов>     repos/autotests
```

Бэкенд — группа из нескольких репозиториев (`core`, `api`, `common`,
`config`): каждая часть клонируется отдельно, в свой каталог. Состав задаёт
`settings.json` (`repos.backend.<часть>.link`); бэкенд в одном репозитории
тоже поддерживается — тогда там обычная запись с `link`.

Клонируйте только то, с чем работаете: аналитику нужен
`repos/system-analysis`, фронтендеру — `repos/frontend`, тестировщику —
`repos/autotests`, бэкендеру — все части бэкенда (таблица «Какая
конфигурация нужна какой команде» — в [README.md](README.md)).

Проверьте результат — повторный `/conveyor:setup` ничего не перезаписывает, а
показывает состояние каждой копии (`ok` / не склонирована / не git-репозиторий
/ ссылка непригодна). То же самое печатает скрипт напрямую:
```
node <plugin>/core/scripts/repos-status.mjs
```

### Шаг 8. (Опционально) Личные настройки в `.env`
`.env` не обязателен: без него действуют умолчания. Нужен — скопируйте
`.env.example` → `.env`; в нём всего две переменные:
- `CONVEYOR_REVIEW_ROUNDS` — раундов цикла ревью (пусто = 2; `0` — ревью
  выключено, не трогая остальное);
- `CONVEYOR_FAST=true` — **быстрый режим** для медленных/слабых моделей:
  ревью отключается, валидация артефактов — скриптом, короче git-контекст
  и диффы. По умолчанию выключен.

Ссылок на репозитории в `.env` нет — они живут в `settings.json`.

### Шаг 9. (Опционально) Запуск автотестов в Jenkins
Этап `/conveyor:implement-auto-test` умеет после push запускать джобу
автотестов и дожидаться результата. Для этого нужны две вещи:

1. **Ссылка на джобу** в `settings.json`:
   `repos.autoTest.linkPipelineAutoTest` — например
   `https://jenkins.example.com/job/MAM/job/autotest-web/`.
2. **MCP-сервер Jenkins**, подключённый в вашем клиенте (Claude Code —
   в конфигурации MCP; GigaCode — если поддержка MCP есть в вашей сборке).
   Плагин его не устанавливает и не настраивает. Какой именно сервер — не
   важно: имена инструментов нигде не прописаны, этап подбирает их в сессии
   сам (запуск сборки, статус, результаты тестов) и спрашивает вас, если
   подходящих окажется несколько.

**Токен Jenkins живёт в конфигурации MCP-сервера**, а не в `settings.json` и
не в `.env` конвейера: в репозиторий команды попадает только ссылка на джобу.

Ничего из этого не настроено — этап работает как раньше: тесты пишутся,
коммитятся, а в отчёте в разделе «Прогон в CI» пишется, что джоба с
автотестами не запускалась.

Готово — можно запускать `/conveyor:intent`.

### Обновление / удаление
```
gigacode extensions uninstall conveyor          # снять
node scripts/build.mjs                           # пересобрать после правок
gigacode extensions install dist/gigacode        # поставить заново
```

## B. Claude Code

### Шаг 1–3. Собрать (те же шаги)
```
cd путь/к/conveyor
node scripts/build.mjs        # появится dist/claude-code/
node scripts/check.mjs        # опционально
```
`dist/claude-code/` — готовый плагин: внутри `.claude-plugin/plugin.json`,
`skills/`, `agents/`, `hooks/`, `core/`.

### Шаг 4. Подключить как плагин
Укажите Claude Code на каталог `dist/claude-code/` как локальный плагин
(команда `/plugin` → установка из локального пути, либо добавление каталога в
настройки плагинов — способ зависит от версии Claude Code).

Ставьте именно ПЛАГИНОМ. Скиллы, скопированные в `.claude/skills/` проекта,
Claude Code плагином не считает и путь плагина в SKILL.md не подставляет —
этап встанет на первой же команде: скрипты будут искаться по несуществующему
пути.

### Шаг 5. Проверить и инициализировать
Команды доступны как `/conveyor:<имя>` (или короткой формой `/<имя>`, если нет
конфликта со встроенными). Запустите `/conveyor:setup`, затем склонируйте
репозитории в `repos/*` и при желании заведите `.env` — как в шагах 6–8 выше.

Отличие от GigaCode: в Claude Code защита работает через хуки автоматически, и
хук `SessionStart` при старте сессии сам скажет, каких рабочих копий не хватает;
в GigaCode — через сами команды (см. `adapters/gigacode/README.md`).

## Обновление рабочего репозитория с версии 1.x

Если рабочий репозиторий заведён conveyor 1.x (ссылки `${VAR}` в
`settings.json`, `.cache/repos/`, `feature.md` в папках задач) — переведите его
скриптом `core/scripts/migrate-workspace.mjs`, СНАЧАЛА без `--apply` (сухой
прогон). Что именно он меняет и как продолжаются начатые задачи — раздел
«Обновление с 1.x» в [README.md](README.md).

## Устранение проблем

| Симптом | Причина и решение |
|---|---|
| `gigacode extensions list` не показывает conveyor; при установке был `Only gigacode-extension.json is supported` | Манифест назван неверно. Он ОБЯЗАН быть `gigacode-extension.json`. Проверьте `dist/gigacode/gigacode-extension.json`, пересоберите (`node scripts/build.mjs`) и поставьте через `gigacode extensions install`. |
| Команды `/conveyor:*` не появились | Расширение скопировано вручную (`cp -r`) — оно не зарегистрировано. Снимите (`gigacode extensions uninstall conveyor`) и поставьте через `gigacode extensions install dist/gigacode`. |
| Скрипты падают: `node: command not found` | Нет Node.js в PATH. Установите Node.js ≥ 14. |
| При запуске команды — «Здесь не инициализирован рабочий репозиторий conveyor» | Не выполнен `/conveyor:setup` в этом каталоге, либо нет `settings.json`. Запустите `/conveyor:setup`. |
| Этап останавливается: рабочая копия не склонирована | В `repos/<каталог>` пусто. Склонируйте туда репозиторий (шаг 7) — плагин этого не делает. Состояние всех копий покажет `/conveyor:setup`. |
| Этап останавливается: в `repos.*.link` git-URL или путь наружу | В `settings.json` нужен путь ВНУТРИ рабочего репозитория (`repos/frontend`, `repos/backend/api`). git-URL и пути вроде `../frontend` guard-скрипты не принимают. Поправьте `settings.json` и закоммитьте — он общий для команды. |
| `/conveyor:setup` жалуется на форму настроек (лишний ключ в `repos`, вложенные записи не под `backend`) | Группой репозиториев может быть только `backend`; остальные ключи — обычные записи с `link`. Лишние ключи в `repos` плагин не использует и называет их прямо. |
| `/conveyor:implement-plan` останавливается: «план не говорит, где править» | В `plan.md` нет раздела «Затронутые репозитории», у шагов нет тега `Репозиторий:` либо таблица разошлась с шагами. Лечится возвратом на `/conveyor:create-plan`. |
| Запись в репозиторий блокируется: «вне рабочей области текущего этапа» | Остался след прерванного этапа. Снимите область: `node <plugin>/core/scripts/scope.mjs clear` (сама она снимается по TTL 8 ч и на старте сессии). |
