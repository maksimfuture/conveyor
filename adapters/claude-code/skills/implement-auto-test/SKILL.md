Этап конвейера conveyor: реализация автотестов.
**Агент:** qa-autotest-engineer. **Предусловие:** есть autotest-plan.md
(`meta.json → stages['autotest-plan'].done`). implement-plan НЕ ждём: тесты
пишутся параллельно с разработкой.

**Корень плагина.** `${CLAUDE_PLUGIN_ROOT}` — Claude Code подставил сюда
абсолютный путь при загрузке скилла. Ниже и во всех файлах этапа он обозначен
плейсхолдером `<CONVEYOR_ROOT>`: подставляй этот путь БУКВАЛЬНО в каждую
команду и каждый путь. Переменной окружения с таким именем нет — `$` с
фигурными скобками раскроется в пустоту, а окружение между вызовами Bash не
сохраняется. Остался незаменённый текст вместо пути — возьми каталог из строки
«Base directory for this skill» выше и поднимись на два уровня.

Прочитай и выполни точно: `<CONVEYOR_ROOT>/core/stages/_common.md` и
`<CONVEYOR_ROOT>/core/stages/implement-auto-test.md`.

Кратко:
1. resolve-config; задача из meta.json. Установи рабочую область:
   `scope.mjs set --stage implement-auto-test --type <FE|BE> --task
   <TASK-ID>` (запись — только репо автотестов; `clear` при завершении).
   Проверь чистоту working tree репозитория автотестов.
2. Обнови копию автотестов (`update --mode write`); создай ветку
   `<TASK-ID>-autotests` (`git-ops branch`), запиши autotestBranch.
3. Запусти qa-autotest-engineer: вход — ТОЛЬКО autotest-plan.md,
   specification.md и путь к рабочей копии автотестов (кодовая база FE/BE
   не открывается, дифф реализации не готовится); реализация автотестов
   из таблицы «Автотесты» плана («Класс» — куда, «Реализация» — что именно)
   по соглашениям репозитория автотестов, с отметкой колонки «Статус» каждой
   выполненной строки в autotest-plan.md
   (`[ ]` → `[x]`; остальной текст плана не правится) и локальный прогон
   тестов. Отчёт на этом шаге НЕ пишется — сначала ревью (шаг 4). Тест падает
   потому, что функционала ещё нет, — НЕ подгоняй его под старое поведение:
   проверка остаётся по спецификации, причина — «функционал ещё не
   реализован».
4. Цикл ревью (core/stages/_review-loop.md, домен autotests): агент reviewer
   находит замечания, qa-autotest-engineer спорит и исправляет (2 раунда по
   умолчанию; нерешённые blocker/major → эскалация). Итог — в meta.json
   (`review`), оттуда он попадёт в раздел «Ревью» отчёта.
5. Отчёт (без CI): запусти qa-autotest-engineer второй раз — вход
   autotest-plan.md, результаты локального прогона и `review` из meta.json;
   выход — report-auto-test.md, заполненный целиком, КРОМЕ «Прогона в CI»:
   там ссылка на джобу и ветка, а «Сборка» и «Статус» — «ожидается прогон в
   CI». Сразу сверь с планом:
   `validate-artifact --file <задача>/report-auto-test.md --type report-auto-test --plan <задача>/autotest-plan.md`
   — на каждую строку таблицы «Автотесты» плана строка в отчёте с тем же ID;
   `planMismatch.missing` → возврат
   агенту; `extra` → должен быть объяснён в «Расхождении с планом».
   `ciPending: true` здесь — норма. Сверка до сборки не случайна: потерянный
   тест — это ещё и недостающий тег, то есть лишний прогон джобы.
6. Скилл коммитит финальные изменения в ветку и спрашивает про push: пушу я /
   пушите сами (дождись подтверждения) / не пушить. MR — по отдельному
   подтверждению.
7. Обнови meta.json: stages.implement-auto-test.done + review. Отчёт остаётся
   с маркером «ожидается прогон в CI» (`ciPending: true` — норма): джобу в
   Jenkins запускает и «Прогон в CI» дописывает `/conveyor:run-auto-test`.
   `scope.mjs clear`. Следующий шаг — `/conveyor:run-auto-test` (когда
   implement-plan завершён и функционал на стенде).
