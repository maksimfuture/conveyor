# Общие правила для всех этапов конвейера conveyor

Эти правила действуют на каждом этапе; отдельные stage-файлы на них ссылаются.

## Пути и запуск скриптов
- `${CONVEYOR_ROOT}` — корень установленного плагина. В Claude Code это
  `${CLAUDE_PLUGIN_ROOT}`. SKILL.md задаёт это значение перед первым вызовом.
- Вся исполняемая логика — в `${CONVEYOR_ROOT}/core/scripts/*.mjs`. Вызывай
  их через `node`. Скиллы и агенты НЕ читают `.env` напрямую.
- НИКАКИХ cmd.exe-идиом (`dir /b`, `> nul`, `del`, `copy`, `type`) — даже
  на Windows оболочка bash-подобная: `> nul` СОЗДАЁТ файл nul. Вывод
  отбрасывай в `/dev/null`; существование файла проверяй инструментами
  платформы (Read/Glob) или `node -e "...fs.existsSync..."`.

## Первый шаг любого этапа (кроме /setup и /task-status)
1. Получи конфигурацию:
   `node "${CONVEYOR_ROOT}/core/scripts/resolve-config.mjs"`
   Разбери JSON: `found`, `workspaceRoot`, `config`, `links`, `missingLinks`,
   `urlLinks`, `fastMode`.
2. Если `found:false` — останови этап: «Здесь не инициализирован рабочий
   репозиторий conveyor. Запустите /setup».
3. Останови этап, если репозиторий, нужный ЭТОМУ этапу (таблица «Какая
   конфигурация нужна какой команде» в README), непригоден по любой из трёх
   причин: он в `missingLinks` (ссылка не задана),
   в `urlLinks` (вместо пути задан git-URL) или у него
   `links.<ключ>.inside == false` (путь ведёт за пределы рабочего
   репозитория). Объясни пользователю: в settings.json `repos.<ключ>.link` —
   это путь ВНУТРИ рабочего репозитория, вида `repos/frontend`, а сам
   репозиторий разработчик клонирует туда сам: плагин не клонирует. Затем
   предложи `/setup`.

## Определение задачи
Раздел применяется к этапам, которые работают с УЖЕ заведённой задачей:
`create-plan`, `implement-plan`, `create-autotest-plan`, `implement-auto-test`.

- TASK-ID берётся из аргумента. Если не передан — предложи выбор: до 3
  последних незавершённых задач из `tasks/` + вариант «введу TASK-ID вручную».
- Тип задачи (FE/BE) и все поля берутся из `tasks/<FE|BE>/<TASK-ID>/meta.json`.

**Исключения — этапы, у которых задачи ещё нет:**
- `intent` работает с намерением, а не с задачей: у него свой идентификатор
  `INTENT-N`, ни `meta.json`, ни папки задачи нет (см. `intent.md`);
- `create-specification` задачу ЗАВОДИТ: её аргументом может быть `INTENT-ID`
  (новая задача) или `TASK-ID` (продолжение начатой); при пустом аргументе он
  предлагает intent'ы, на которые ещё не ссылается ни одна задача; тип
  (`FE`/`BE`/`FE-BE`) и номер новой задачи спрашиваются у аналитика, а
  `meta.json` появляется только по ходу фазы A (см. `create-specification.md`).

## Рабочая область этапа (scope) — агенты НЕ гуляют по репозиториям
Каждый этап работает СТРОГО со своими репозиториями. После определения
этапа и типа задачи установи рабочую область:
`node "${CONVEYOR_ROOT}/core/scripts/scope.mjs" set --stage <этап> --type <FE|BE> --task <TASK-ID>`
— guard-скрипты будут блокировать запись в рабочие копии всех остальных
репозиториев. При завершении этапа: `... scope.mjs clear`.
У этапа `intent` типа задачи ещё НЕ существует, поэтому вызов другой:
`... scope.mjs set --stage intent --task <INTENT-ID>` — без `--type`
(переданный тип scope.mjs отвергает: он был бы выдумкой).

| Этап | АГЕНТ читает | АГЕНТ пишет |
|---|---|---|
| intent | анализ (systemsAnalysis), read-only | — (только `intents/<INTENT-ID>/`) |
| create-specification (фаза A) | анализ | анализ |
| create-specification (фаза B) | анализ | — (только артефакты задачи) |
| create-plan | код FE/BE (по типу) | — (только артефакты) |
| implement-plan | код FE/BE | код FE/BE |
| create-autotest-plan | автотесты (autoTest), read-only + артефакты | — (только артефакты) |
| implement-auto-test | автотесты (autoTest) | автотесты |

(Колонки — про АГЕНТА: сама команда может читать кодовую базу для подготовки
диффов через git-ops — например, на фазе B create-specification. Фаза B
снимает право записи в анализ вызовом `scope.mjs set … --write none`. На
create-autotest-plan и implement-auto-test кодовая база FE/BE не открывается
вовсе.)

Правила:
- агенту передаются ТОЛЬКО пути его области (см. таблицу) + папка задачи
  (на `intent` — папка намерения); пути других репозиториев агенту не
  сообщаются;
- git-данные чужих репозиториев (диффы) готовит команда через git-ops и
  передаёт агенту текстом — агент в те репозитории не заходит;
- в папках артефактов (`tasks/<FE|BE>/<TASK-ID>/` и `intents/<INTENT-ID>/`)
  ты пишешь ТОЛЬКО артефакт СВОЕГО этапа плюс `meta.json`. Артефакты соседних
  этапов не создавай и не заполняй «заранее»: каждый производит их сам, и
  guard чужой артефакт блокирует. Кто что производит:

  | Этап | Артефакт |
  |---|---|
  | intent | `intent.md` |
  | create-specification | `specification.md` |
  | create-plan | `plan.md` |
  | implement-plan | `plan.md` (отметки шагов, отклонения, ревью) |
  | create-autotest-plan | `autotest-plan.md` |
  | implement-auto-test | `report-auto-test.md` |

  ИСХОДНИКИ (tsx/js/adoc/…) пишутся ТОЛЬКО в рабочую копию соответствующего
  репозитория, НИКОГДА в папку задачи или намерения;
  при активном этапе в рабочем репозитории запись разрешена ТОЛЬКО в
  `tasks/`, `intents/` и файлы конфигурации в корне (`settings.json`,
  `.env`, `.env.example`, `.gitignore`) — НИКАКИХ пробных файлов
  («test-write.txt») для «проверки записи»: вызов guard-скрипта сам
  является проверкой (dry-run), временные файлы — только в системном temp;
- останавливая этап ДОСРОЧНО (ошибка, грязная копия, эскалация, отказ
  пользователя) — тоже сними область (`scope.mjs clear`); впрочем,
  устаревшая область безопасна: следующий `set` её перезаписывает, а через
  8 часов она игнорируется (TTL) и снимается на старте сессии.

## Работа с внешними репозиториями (спец. 4.3)
- Найти рабочую копию:
  `node "${CONVEYOR_ROOT}/core/scripts/git-ops.mjs" locate --link <link> --workspace <workspaceRoot> --name <key>`
  (`link` — путь ОТ корня рабочего репозитория, поэтому `--workspace` обязателен)
- Обновить перед работой:
  `... git-ops.mjs update --path <repoPath> --main <mainBranch> --mode read|write`
  Рабочая копия принадлежит разработчику: его ветку этап не переключает —
  update подтягивает только основную ветку.
  Для этапов записи (`--mode write`) грязная локальная копия → остановка.
- Диффы «ветка задачи vs основная» — merge-base-семантика:
  `... git-ops.mjs diff --path <repoPath> --base <mainBranch> --head <branch>`
  (возвращает `baseSha` = merge-base, `headSha`, `diff`).

## Идемпотентность
Повторный запуск этапа предлагает: перезаписать / дополнить / отменить.
Молча не перезаписывай. «Дополнить» = передать агенту текущий артефакт и
попросить сохранить существующие ID (REQ-*, ID кейсов) и нумерацию, добавляя
новые с продолжением.

## Завершение этапа
ПЕРЕД тем как ставить done — проверь чистоту папки задачи:
`node "${CONVEYOR_ROOT}/core/scripts/validate-task-folder.mjs" --task <абс. путь к папке задачи>`
При `ok:false` в папку задачи попали посторонние файлы (обычно исходники,
которые агент положил не туда): перенеси правки кода в рабочую копию
кодовой базы (если они по плану) либо удали лишнее, и повтори проверку.
Этап НЕ считается завершённым, пока проверка не зелёная.
Затем обнови `meta.json` (соответствующий `stages.<этап>.done = true`, при
наличии — `baseSha`/`headSha`). Напечатай пользователю: что создано/изменено,
где лежит, какой этап следующий.

## Запуск агента
Агент не видит контекст сессии. Передай ему в промпте: абсолютные пути к
папке задачи и рабочим копиям, разрешённую конфигурацию (без секретов),
подготовленные git-диффы. Тело промпта роли — в
`${CONVEYOR_ROOT}/core/prompts/<агент>.md`.

**Файлы соглашений репозитория — агенту первым делом.** Перед запуском
агента проверь в корне его рабочей копии файлы соглашений (в порядке
приоритета): `.gigacode/rules/*.md`, `GIGACODE.md`, `CLAUDE.md`,
`AGENTS.md`. Если найдены — ВСТАВЬ их текст в промпт агента (суммарно до
~200 строк; длиннее — передай пути с указанием «прочитай первыми») и
скажи агенту: «следуй этим соглашениям; исследуй кодовую базу сам только
по вопросам, которые ими не покрыты». Это сильно сокращает исследование
репозитория (особенно на слабых моделях). Нет файлов — агент изучает
соглашения сам, как раньше.

**Шаблон артефакта — текстом, не ссылкой.** Если этап производит артефакт
(intent.md, specification.md, plan.md, autotest-plan.md,
report-auto-test.md), вставь в промпт агента ПОЛНЫЙ текст соответствующего
шаблона из `${CONVEYOR_ROOT}/core/templates/<имя>.md` — агент заполняет
этот каркас, не меняя структуру разделов. Не полагайся на то, что агент
сам прочитает файл шаблона (слабая модель может «заполнить по памяти»).

## Быстрый режим (config.fast, env CONVEYOR_FAST; по умолчанию ВЫКЛЮЧЕН)
Для медленных/слабых моделей. Если `resolve-config` вернул `fastMode: true`:
- цикл ревью НЕ запускается (resolve-config уже вернул reviewRounds = 0);
- валидацию артефактов выполняй скриптом, а не повторным прогоном агента:
  `node "${CONVEYOR_ROOT}/core/scripts/validate-artifact.mjs" --file <путь>
  --type <intent|specification|plan|autotest-plan|report-auto-test>`
  — при `ok:false` один возврат агенту со списком `missingSections`/`problems`;
- git-контекст короче: `git-ops log -n 5`; дифф длиннее ~400 строк усекай:
  полный список файлов + первые ~200 строк диффа;
- уточнения у пользователя объединяй в ОДИН вопрос с вариантами;
- в промпт агенту добавляй: «Быстрый режим: заполняй только обязательные
  разделы шаблона, кратко, без развёрнутых рассуждений».

## Уточнения у пользователя (запрос агента)
Агент, столкнувшись с существенной неопределённостью, не гадает, а вместо
результата возвращает ЗАПРОС НА УТОЧНЕНИЕ (список конкретных вопросов). В этом
случае: задай эти вопросы пользователю через AskUserQuestion (варианты +
возможность ввести свой ответ), затем перезапусти того же агента, добавив
ответы в его контекст.
Не подставляй ответы за пользователя и не пропускай вопрос молча.
