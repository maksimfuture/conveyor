# Общий цикл ревью (_review-loop.md)

Применяется на этапах, где агент ПРОИЗВОДИТ содержимое:
- фаза A этапа `/conveyor:create-specification` — правки документов
  репозитория системного анализа (домен `systems-analysis`); цикл идёт по
  этим правкам, а не по спецификации: её собирает фаза B, уже из отревьюенного
  диффа;
- `/conveyor:implement-plan` — код (домен `frontend` или `backend` по типу
  задачи);
- `/conveyor:implement-auto-test` — автотесты (домен `autotests`).

Участники: **producer** — агент этапа; **reviewer** — агент `reviewer`
(`${CONVEYOR_ROOT}/core/prompts/reviewer.md`) с указанным доменом. Оба —
субагенты: контекст сессии не видят, скилл ЗАНОВО запускает их на каждом
раунде, реконструируя нужный контекст в промпте (см. «Оркестрация»).

Число раундов: `settings.json → reviewRounds` (по умолчанию **2**). Значение
`0` — ревью выключено (см. «reviewRounds = 0»). Блокируют переход к
следующему этапу только findings severity **blocker** и **major**; minor
исправляются по возможности и переход не блокируют.

## Что ревьюит reviewer (diff)
Ревью идёт ДО коммита (коммит — после ревью), поэтому произведённая работа
лежит в рабочей копии НЕзакоммиченной. Скилл передаёт reviewer **дифф
рабочего дерева** (незакоммиченные изменения), а НЕ дифф между коммитами:
например `git diff` рабочего дерева против головы ветки задачи (для кода
и тестов) или список изменённых файлов рабочей копии анализа. На повторных
раундах — накопленные незакоммиченные правки.

## Раунд
Один раунд = review → ответ/спор → фикс:
1. Reviewer ревьюит текущее состояние (working-tree дифф + source-of-truth) и
   возвращает findings (`id`, `severity`, `location`, `problem`,
   `suggestedFix`, `rationale`).
2. Если у reviewer 0 findings severity blocker|major → **успех**, цикл
   завершён (openIssues = 0).
3. Иначе producer отвечает на каждый blocker|major finding: `ACCEPT`
   (исправлю) или `REBUT` (с техническим обоснованием).
4. Спор: reviewer один раз пересматривает REBUT-findings — `withdraw`
   (снимает) или `hold` (подтверждает с контраргументом).
5. Producer вносит правки:
   - все ACCEPT — исправляет;
   - HELD (reviewer подтвердил) — producer либо соглашается и исправляет,
     либо **остаётся при своём мнении** (мотивированно) — тогда finding
     помечается `unresolved` и НЕ исправляется;
   - REBUT-withdrawn — пропускает.

Затем начинается следующий раунд: reviewer ревьюит исправленный результат
(верифицируя правки и ища новое), пока не станет 0 blocker|major ЛИБО не
исчерпаны `reviewRounds`.

## Завершение и openIssues
- **Финальная верификация:** после правок последнего раунда reviewer делает
  один короткий проверочный проход (НЕ считается раундом), чтобы правки
  последнего раунда не уходили без переревью.
- `openIssues` = число blocker|major, оставшихся после этого прохода:
  `unresolved` (producer не согласился с HELD) + любые непочиненные/вновь
  найденные blocker|major.
- Если `openIssues > 0` — **эскалация:** НЕ игнорируй и не завершай молча.
  Покажи пользователю по каждому нерешённому пункту обе позиции (reviewer и
  producer) и дай решить (исправить по reviewer / принять как есть / свой
  вариант). Этап завершается только после решения пользователя; принятые
  «как есть» пункты остаются в разделе «Ревью» как сознательно принятые.

## Запись итога
- В артефакт этапа (specification.md / plan.md / report-auto-test.md) — раздел
  **«Ревью»**: сколько раундов, что исправлено, что отклонено (REBUT→withdraw
  с обоснованием), нерешённые (unresolved) и решение пользователя по ним.
- `meta.json → stages.<этап>`:
  `"review": { "rounds": <факт>, "openIssues": <число>, "fixed": [<кратко>],
  "rebutted": [<finding — обоснование>], "unresolved": [<blocker|major — позиции>] }`.
  Три списка нужны потому, что артефакт этапа не всегда пишется в том же
  прогоне, что и ревью: на `/conveyor:create-specification` цикл идёт в фазе A,
  а раздел «Ревью» заполняется в фазе B, которая после обрыва запускается
  ОТДЕЛЬНОЙ сессией. Держать эти данные только в контексте сессии нельзя —
  продолженный прогон их не увидит и либо оставит каркас, либо выдумает.
  Заполняя раздел «Ревью» артефакта, бери содержимое ИЗ ЭТОГО объекта.
  Объекта нет (ревью не запускалось, `reviewRounds: 0`, задача мигрирована
  с 1.x) — так и напиши в разделе; НЕ придумывай замечания задним числом.
- Идемпотентность: при повторном запуске этапа раздел «Ревью» и объект
  `review` относятся к ПОСЛЕДНЕМУ прогону цикла (перезапись, не накопление).

## Оркестрация (кто кого запускает)
Producer и reviewer — субагенты без общей памяти. За раунд скилл делает
отдельные вызовы:
1. reviewer(домен, source-of-truth, working-tree дифф, пути) → findings;
2. producer(текущий артефакт/дифф + findings) → ACCEPT/REBUT по каждому;
3. reviewer(REBUT-findings + обоснования producer) → withdraw/hold;
4. producer(итог withdraw/hold) → вносит правки, помечает unresolved.
Каждый вызов реконструирует контекст в промпте (агенты не помнят прошлых
вызовов). Правки по findings вносит тот же producer-агент этапа.

## reviewRounds = 0
Ревью выключено: producer работает без ревью. Скилл всё равно пишет
`"review": { "rounds": 0, "openIssues": 0 }` в meta.json и в разделе «Ревью»
артефакта помечает «ревью отключено (reviewRounds=0)». DoD «цикл ревью
пройден» при 0 считается выполненным без ревью.

## FE-BE пара (только /conveyor:create-specification)
Правки анализа у пары ОДНИ: они идут в общей ветке `analysisBranch`,
именованной по INTENT-ID. Поэтому в фазе A цикл запускается ОДИН раз — на эти
общие правки; двух ревью не бывает. Объект `review` пишется в `meta.json`
ОБЕИХ задач (единый итог, ссылки на `relatedTaskId`).
Спецификаций при этом две: в фазе B агент разносит требования по
`specification.md` FE- и BE-задачи, и раздел «Ревью» — с одним и тем же
содержимым из `review` — заполняется в ОБЕИХ.

## Замечания
- reviewer код не правит — только findings; правки вносит producer.
- reviewer проверяет утверждения запуском (тесты/репро/линтеры), а не на слово,
  но НЕ грязнит рабочую копию: наведённые прогоном файлы (снапшоты, покрытие,
  lock) не коммитятся — коммитятся только изменения по задаче (§ стейджей).
- guard-хуки (запись/git) действуют и во время ревью-правок как обычно.
