# Этап /conveyor:create-autotest-plan — план автотестов

**Кто запускает:** QA. **Агент:** qa-autotest-engineer
(`<CONVEYOR_ROOT>/core/prompts/qa-autotest-engineer.md`).
**Аргументы:** `TASK-ID`.
**Предусловие:** этап `implement-plan` завершён (meta.json).

Суть: по спецификации задачи составить план автотестов. Тесты проверяют
СПЕЦИФИКАЦИЮ, а не реализацию, поэтому кодовая база на этом этапе не
открывается и дифф реализации не готовится — ни агентом, ни командой. Так план
способен ПОЙМАТЬ расхождение реализации с требованиями, а не закрепить его.

**Рабочая область:** чтение — `specification.md` (единственный артефакт
задачи на входе) и репозиторий автотестов (соглашения + существующие тесты);
запись — только артефакты задачи. Кодовые базы FE/BE и репозиторий анализа
не открываются и агенту не сообщаются.

## Алгоритм
1. Первый шаг — resolve-config (см. `_common.md`): нужна ссылка `autoTest`,
   её нет в `missingLinks`/`urlLinks` — иначе останови этап. Тип задачи
   (FE/BE) и завершённость `implement-plan` — из
   `docs/specs/tasks/<FE|BE>/<TASK-ID>/meta.json`.
2. Установи рабочую область:
   `scope.mjs set --stage create-autotest-plan --type <FE|BE> --task <TASK-ID>`
   (запись в репозитории запрещена: репозиторий автотестов этот этап только
   читает, писать в него будет `/conveyor:implement-auto-test`).
3. Найди рабочую копию автотестов (`git-ops locate`) и обнови её
   (`git-ops update --mode read` — этап только читает; грязная копия здесь НЕ
   является ошибкой, просто предупреждение). Собери файлы соглашений
   репозитория (см. `_common.md`, «Запуск агента»).
4. Идемпотентность: `autotest-plan.md` в папке задачи уже есть — предложи
   «дополнить / перезаписать / отмена» (см. `_common.md`); «дополнить» —
   сохранить существующие ID кейсов и продолжить нумерацию.
5. Запусти qa-autotest-engineer: вход — `specification.md` (ЕДИНСТВЕННЫЙ
   артефакт задачи, который получает агент), путь к рабочей копии автотестов
   ТОЛЬКО ДЛЯ ЧТЕНИЯ (соглашения, существующие фикстуры и уже покрытые
   сценарии — чтобы переиспользовать их и не плодить дубли), файлы
   соглашений, ПОЛНЫЙ текст `core/templates/autotest-plan.md`. Выход —
   `autotest-plan.md` в папке задачи. Пути к кодовым базам НЕ передавать.
   `plan.md` агенту НЕ передавать: его «Отклонения и остатки» — рассказ о
   том, что получилось в реализации, и план, написанный с оглядкой на них,
   закрепит расхождение вместо того, чтобы его поймать. Это та же причина,
   по которой сюда не идут дифф и кодовая база.
6. Агент вернул запрос на уточнение — задай вопросы пользователю через
   AskUserQuestion и перезапусти его с ответами (см. `_common.md`).
7. Валидация:
   `node "<CONVEYOR_ROOT>/core/scripts/validate-artifact.mjs" --file <папка задачи>/autotest-plan.md --type autotest-plan`
   плюс покрытие: каждый критерий приёмки спецификации закрыт хотя бы одним
   тест-кейсом либо явно помечен «не автоматизируется» с причиной. Плюс
   сводка: «Итого» не противоречит таблицам выше (счётчики кейсов,
   автотестов и файлов сходятся с таблицами «Тест-кейсы» и «Автотесты») —
   валидатор проверяет состав колонок обеих таблиц, заполненность колонки
   «Статус» у каждого автотеста, сходимость колонки «Автотест» с таблицей
   автотестов, что каждый кейс попал либо в «Автотесты», либо в «Что не
   автоматизируем», наличие обоснования выбора регресса под таблицей и
   отсутствие отклонённых уровней в «Уровнях тестирования»;
   сходимость чисел он не считает. Счётчик автотестов из
   «Итого» — это то же число, что `/conveyor:implement-auto-test` сверит с
   отчётом о прогоне, поэтому расхождение с таблицей «Автотесты» здесь
   дороже обычной опечатки.
   Не сошлось — один автоматический возврат агенту, затем покажи
   пользователю остаток.
   Возврат делай не только при `ok:false`, но и при непустом `placeholders`:
   в артефакте остался каркас шаблона, а цикла ревью на этом этапе нет и
   другого сигнала «сюда не написали» не будет.
8. Завершение этапа (см. `_common.md`): `validate-task-folder`, затем
   `meta.json → stages['autotest-plan'].done = true`. Сними рабочую область
   (`scope.mjs clear`).

## Ревью
Цикл ревью на этом этапе НЕ запускается (`_review-loop.md` не подключается) —
он остаётся на `/conveyor:implement-auto-test`, где тесты реально прогоняются.

## Ошибки
- рабочая копия автотестов не найдена → остановка с подсказкой склонировать
  её в путь из `settings.json` (плагин не клонирует);
- спецификации нет в папке задачи → остановка: сначала
  `/conveyor:create-specification`;
- этап `implement-plan` не завершён → остановка: автотесты пишутся и
  прогоняются по готовой функциональности, а следующий этап
  (`/conveyor:implement-auto-test`) запускает их на стенде. Содержимое
  `plan.md` при этом в план автотестов не попадает — предусловие о сроке, а
  не об источнике.

## DoD
`autotest-plan.md` прошёл валидацию шаблона и проверку покрытия критериев
приёмки; тест-кейсы лежат ОДНОЙ таблицей и держат кейс целиком (ID, вид
тестирования, уровень, название, шаги, ожидаемый результат, REQ-ID и
«Автотест» — да/нет, сходится с таблицей автотестов) — отдельных описаний под
таблицей нет; автотесты лежат второй таблицей (тот же
ID, вид, уровень, класс, что именно реализовать, REQ-ID, статус) с
обоснованием выбора регресса под ней; каждый кейс попал либо в «Автотесты»,
либо в «Что не автоматизируем»; ID — идентификаторы тестов в Jira
(`@TmsLink`, у новых — плейсхолдер `T999-N`); «Уровни тестирования» называют
только те уровни, на которых будут тесты; «Итого» стоит внизу и сходится с
таблицами выше; остатки каркаса
(`placeholders`) устранены либо показаны пользователю; рабочая область
снята. Колонка «Статус» остаётся `[ ]` — её отмечает
`/conveyor:implement-auto-test`. Следующий шаг —
`/conveyor:implement-auto-test`.
