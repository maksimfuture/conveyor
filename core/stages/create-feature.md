# Этап /create-feature — внести требования в анализ и завести фичу

**Кто запускает:** системный аналитик. **Агент:** system-analyst
(`${CONVEYOR_ROOT}/core/prompts/system-analyst.md`).
**Аргументы:** `[FE|BE|FE-BE] [номер | TASK-ID] [требования/описание]` — все
опциональны.

Суть: требования из промпта ВНОСЯТСЯ в документы репозитория системного
анализа (агент правит/дополняет их в отдельной ветке), и параллельно
заводится задача с feature.md. Эти правки дадут diff для
/create-specification.

## Разбор аргументов и уточнения
- первый токен `FE`/`BE`/`FE-BE` — тип; следующий токен, если это число или
  полный TASK-ID, — номер; остальное — требования;
- тип не передан → спроси (обязательно);
- номер не передан → спроси (обязательно): предложи автоинкремент
  (максимальный номер по ВСЕМ `tasks/`, FE и BE вместе, +1), пользователь
  может задать свой;
- тип `FE-BE` → уточни у аналитика разделение работ; создай ДВЕ связанные
  задачи в `tasks/FE/` и `tasks/BE/`, каждая со своим TASK-ID и feature.md;
  в meta.json обеих запиши `relatedTaskId`. Переданный номер получает
  FE-задача; номер BE-задачи предложи автоинкрементом и подтверди.

**Рабочая область:** ТОЛЬКО репозиторий системного анализа
(repos.systemsAnalysis) + папка задачи. Кодовые базы и репозиторий
автотестов на этом этапе не открываются и агенту не сообщаются.

## Алгоритм
1. Определи тип, TASK-ID (или пару), title. Установи рабочую область:
   `scope.mjs set --stage create-feature --type <FE|BE> --task <TASK-ID>`
   (для FE-BE пары: `--type FE-BE --task <TASK-ID FE-задачи>` — на область
   записи это не влияет, у этапа она всегда = репозиторий анализа).
   Создай папку(и) задач и `meta.json` с полным скелетом (все шесть stages
   `done:false`; для пары — `relatedTaskId`).
2. Найди рабочую копию анализа (`git-ops locate`) и обнови её
   (`git-ops update --mode write` — этап ПИШЕТ в анализ; грязная локальная
   копия → остановка с показом статуса). Запиши
   `analysisShaAtFeature = mainSha` из ответа update.
3. Создай ветку `<TASK-ID>-analysis` от mainBranch (для пары — одну общую,
   по TASK-ID FE-задачи):
   `git-ops branch --path <repo> --branch <TASK-ID>-analysis --from <mainBranch>`.
   Запиши имя в meta.json (`analysisBranch`). Повторный запуск: существующую
   ветку продолжай; пересоздание — только по подтверждению.
4. Подготовь для агента git-данные: `git-ops log --path <repo>` (недавние
   коммиты и изменённые файлы).
5. Запусти system-analyst: пусть найдёт релевантные разделы, внесёт
   требования в документы анализа (по их структуре) и соберёт feature.md по
   `core/templates/feature.md` (для пары — два, с разделением зон FE/BE).
6. **Цикл ревью** (`${CONVEYOR_ROOT}/core/stages/_review-loop.md`), домен
   `systems-analysis`: reviewer проверяет НЕзакоммиченные правки анализа и
   feature.md, system-analyst отвечает/спорит и исправляет. Итог — в разделе
   «Ревью» feature.md; нерешённые blocker|major → эскалация пользователю.
   FE-BE пара: ревью запускается ОДИН раз на общие правки анализа + обе
   feature.md; раздел «Ревью» и объект `review` дублируются в обе feature.md
   и в meta.json обеих задач.
7. Закоммить финальные (после ревью) правки анализа в ветку (сообщение с
   TASK-ID). git commit выполняет скилл. Push/MR — только по подтверждению.
8. Обнови meta.json (`stages.feature.done = true`, объект `review`). Сними
   рабочую область (`scope.mjs clear`). Покажи сводку правок анализа,
   резюме feature.md, итог ревью и открытые вопросы. Следующий шаг —
   `/create-specification`.

## Ошибки
- грязная локальная копия анализа → остановка с показом состояния;
- релевантные разделы не найдены → агент создаёт новый документ/раздел по
  соглашениям репозитория и помечает это в feature.md.

## DoD
Требования внесены в документы анализа и закоммичены в analysisBranch (коммит
— после ревью); папки задач и meta.json созданы; feature.md заполнен(ы) по
шаблону; цикл ревью пройден (нерешённые blocker|major вынесены пользователю).
