# Этап /create-plan — план реализации

**Кто запускает:** разработчик. **Агент и кодовая база** — по типу задачи:
FE → frontend-developer + `codebase.FE`; BE → backend-developer +
`codebase.BE` (пути берутся из settings.json через resolve-config, не
спрашиваются и не угадываются).
**Аргументы:** `TASK-ID`. **Предусловие:** существует `specification.md`.

**Рабочая область:** чтение — ТОЛЬКО кодовая база по типу задачи (ВСЕ юниты
`codebase.<тип>`) + specification.md; запись — ТОЛЬКО артефакты задачи
(plan.md, meta.json). Репозиторий анализа, автотестов и чужая кодовая база не
открываются и агенту не сообщаются.

**Кодовая база бэкенда — несколько репозиториев.** У BE-задачи `codebase.BE`
обычно состоит из `backend.core` (основной код), `backend.api` (API),
`backend.common` (общие утилиты, headers) и `backend.config` (конфигурации).
Раскладка задачи по ним — ЧАСТЬ ПЛАНА, а не деталь реализации: `/implement-plan`
по ней ставит область записи, и в репозиторий, которого нет в плане, guard
писать не даст.

## Алгоритм
1. Определи тип задачи из meta.json → выбери агента и `codebase.<тип>`.
   Установи рабочую область: `scope.mjs set --stage create-plan --type
   <FE|BE> --task <TASK-ID>` (запись в репозитории запрещена).
2. Для КАЖДОГО юнита из `codebase.<тип>`: найди рабочую копию
   (`git-ops locate --link <units[].link> --workspace <root> --name <id>`) и
   обнови (`update --mode read`). Непригоден хотя бы один — останови этап и
   покажи, что склонировать (см. `_common.md`, первый шаг).
3. Запусти агента-разработчика. Вход: specification.md + ТАБЛИЦА рабочих
   копий — на каждую строку `id`, абсолютный путь, `mainBranch`,
   `description` из настроек и файлы соглашений этого репозитория (см.
   `_common.md`, «Запуск агента»; у каждого репозитория они свои). Он обязан
   изучить архитектуру и соглашения и составить `plan.md` по
   `core/templates/plan.md`.
   В промпте явно потребуй:
   - заполнить раздел «Затронутые репозитории» — только те копии, которые
     будут ПРАВИТЬСЯ (что меняем, почему именно здесь, порядок мержа) плюс
     строку про зависимости между ними;
   - у КАЖДОГО шага указать `Репозиторий: <id>`;
   - состав таблицы и теги шагов обязаны совпасть.
4. Валидация (скилл):
   `node "<CONVEYOR_ROOT>/core/scripts/validate-artifact.mjs" --file <папка задачи>/plan.md --type plan --workspace <workspaceRoot> --taskType <FE|BE>`
   (`--workspace` сверяет id репозиториев с settings.json, `--taskType` — что
   план не назвал репозиторий ЧУЖОЙ кодовой базы: такой id существует, и без
   этой сверки его пропустили бы и валидатор, и guard)
   плюс покрытие: каждый шаг привязан к файлам, есть раздел рисков, каждый
   REQ-ID спецификации покрыт хотя бы одним шагом либо явно указано, почему
   требование вне плана. Не сошлось — один автоматический возврат агенту,
   затем покажи пользователю остаток.
   Возврат делай не только при `ok:false`, но и при непустом `placeholders`:
   в артефакте остался каркас шаблона, а цикла ревью на этом этапе нет и
   другого сигнала «сюда не написали» не будет.
5. `validate-task-folder` (см. `_common.md`, «Завершение этапа»), затем
   обнови meta.json: `stages.plan.done = true` и `stages.plan.repos` —
   список из `planRepos.repos` ответа валидатора. Сними рабочую область
   (`scope.mjs clear`). Покажи пользователю таблицу «репозиторий → что
   меняем → порядок мержа» из плана: это главное, что он должен проверить
   перед реализацией.

## Ошибки
- кодовая база недоступна → остановка с инструкцией (см. `_common.md`,
  «Работа с внешними репозиториями»); называй КОНКРЕТНЫЕ непригодные юниты,
  а не «кодовая база»;
- валидация покрытия REQ-ID не прошла → один автоматический возврат агенту со
  списком непокрытых REQ-ID; после повторной неудачи — покажи пользователю,
  что осталось непокрытым;
- план не называет репозиториев (пустая таблица, шаги без тега, таблица и
  шаги разошлись) → возврат агенту с текстом `problems` валидатора: без этого
  списка `/implement-plan` не сможет поставить область записи.

## DoD
План прошёл валидацию покрытия REQ-ID и раскладки по репозиториям;
пользователь видел таблицу затронутых репозиториев. Следующий шаг
— `/implement-plan`.
