# Этап /conveyor:create-specification — правки анализа + спецификация

**Кто запускает:** системный аналитик. **Агент:** system-analyst
(`${CONVEYOR_ROOT}/core/prompts/system-analyst.md`).
**Аргументы:** `INTENT-ID | TASK-ID [FE|BE|FE-BE] [номер]`.
**Предусловие:** для `INTENT-ID` — существует `intents/<INTENT-ID>/intent.md`;
для `TASK-ID` — существует `tasks/<FE|BE>/<TASK-ID>/meta.json` (так
продолжают уже заведённую задачу).

Этап состоит из двух фаз. **Фаза A** — агент вносит требования из intent'а в
документы репозитория системного анализа (единственная фаза конвейера, где
этап пишет в чужой репозиторий). **Фаза B** — по диффу СВОИХ ЖЕ правок
собирается `specification.md`. Между фазами меняется рабочая область.

## Разбор аргументов
- первый аргумент — `INTENT-ID` (новая задача) ЛИБО `TASK-ID` уже заведённой
  задачи (продолжение). Что передали — определяй по файлам, а не по виду
  идентификатора: есть `tasks/FE/<аргумент>/meta.json` или
  `tasks/BE/<аргумент>/meta.json` — это TASK-ID; есть
  `intents/<аргумент>/intent.md` — это INTENT-ID; не нашлось ни того, ни
  другого — остановка (см. «Ошибки»);
- аргумент не передан — предложи выбор: intent'ы, на которые не ссылается ни
  одна задача (обратный индекс по `tasks/*/*/meta.json → intentId`), и задачи
  с незавершённым этапом `specification`;
- ПЕРЕД вопросом о типе и номере выясни, не повторный ли это запуск (шаг 2
  фазы A: по TASK-ID задача названа прямо, по INTENT-ID её ищет тот же
  обратный индекс): у повторного запуска задача уже есть, тип
  и номер берутся из её `meta.json`, и спрашивать их НЕЛЬЗЯ — иначе на том же
  intent'е заведётся вторая задача;
- для НОВОЙ задачи тип (`FE`/`BE`/`FE-BE`) и номер задаёт АНАЛИТИК: в
  intent'е их нет, бизнес-аналитик тип задачи не знает. Чего не передал —
  спроси ОДНИМ объединённым вопросом (тип + номер; номер предложи
  автоинкрементом: максимальный номер по всем `tasks/`, FE и BE вместе, +1);
- `FE-BE` → две связанные задачи в `tasks/FE/` и `tasks/BE/`, каждая со
  своим TASK-ID; в meta.json обеих — `relatedTaskId` и общий `intentId`.
  Переданный номер получает FE-задача, номер BE-задачи предложи
  автоинкрементом в том же вопросе.

**Рабочая область:** репозиторий системного анализа — в фазе A на ЗАПИСЬ, в
фазе B ТОЛЬКО на чтение. Кодовые базы и репозиторий автотестов на этом этапе
не открываются и агенту не сообщаются.

## Идемпотентность (важно — этап дорогой)
Подэтапы фиксируются в `meta.json → stages.specification`: `analysisDone`
(правки анализа внесены, отревьюены и закоммичены) и `specDone`
(спецификация собрана).

Повторный запуск РАСПОЗНАЁТСЯ шагом 2 фазы A: запуск по TASK-ID называет
задачу прямо, запуск по INTENT-ID — обратным индексом
`tasks/*/*/meta.json → intentId`. Ветки:
- аргумент — `TASK-ID` → задача читается по нему; `type`, номер,
  `relatedTaskId`, `analysisBranch`, `analysisBaseSha` и подэтапы берутся из
  её `meta.json`, новая задача не заводится, тип и номер не спрашиваются. При
  `analysisDone:true` этап начинается сразу с шага 13 (фаза B). Это
  ЕДИНСТВЕННЫЙ вход для задачи с пустым `intentId`: мигрированным из 1.x
  задачам `migrate-workspace.mjs` ставит `intentId: null` и папки `intents/`
  для них нет — обратный индекс их не найдёт никогда, а запуск с чужим
  INTENT-ID завёл бы ВТОРУЮ задачу и переиграл правки чужого репозитория.
  Дальше — те же ветки по подэтапам, что и ниже;
- аргумент — `INTENT-ID`, задачи с этим `intentId` нет → первый запуск, фаза
  A целиком;
- `analysisDone:false` → фаза A целиком, но задача уже заведена: шаг 4 не
  создаёт её заново, а лишь дополняет недостающие поля `meta.json`;
- `analysisDone:true, specDone:false` → правки чужого репозитория НЕ
  переигрываются. Пропускаются шаги 3, 4 и 6–12 (область записи, заведение
  задачи, ветка, агент фазы A, ревью, коммит). ВЫПОЛНЯЮТСЯ всё равно: шаг 1
  (resolve-config — обязательный первый шаг по `_common.md`, из него
  `workspaceRoot`, `links` и `mainBranch`), шаг 2 (распознавание) и из шага 5
  только `git-ops locate` — без него неоткуда взять `--path <repo>` для
  диффа фазы B; `git-ops update` на этом пути не нужен — ветка анализа уже
  закоммичена, и область на запись в анализ не ставится вовсе.
  Дальше — сразу шаг 13 и далее; дифф считается от `analysisBaseSha` до
  вершины ветки `analysisBranch` (оба поля уже в `meta.json`);
- обе `true` → спроси «перезаписать / дополнить / отмена» и уточни, что
  именно: только спецификацию или заново и правки анализа.

## Фаза A — правки репозитория анализа
1. Первый шаг — resolve-config (см. `_common.md`): нужна ссылка
   `systemsAnalysis`, её нет в `missingLinks`/`urlLinks` — иначе останови
   этап. Прочитай `intents/<INTENT-ID>/intent.md` (при запуске по TASK-ID
   intent'а может не быть вовсе — см. шаг 15).
2. Повторный ли это запуск? Аргумент-`TASK-ID` отвечает на это сам: задача —
   `tasks/<FE|BE>/<TASK-ID>/meta.json`. Аргумент-`INTENT-ID` — пройди
   обратный индекс `tasks/*/*/meta.json → intentId` и найди задачи с этим
   `intentId` (у пары FE-BE их две). Задача нашлась — новую НЕ заводи и тип с
   номером у пользователя НЕ спрашивай: `taskId`, `type`, `relatedTaskId`,
   `analysisBranch`, `analysisBaseSha` и подэтапы `stages.specification` бери
   из её `meta.json`, дальше действуй по ветке раздела «Идемпотентность» (при
   `analysisDone:true` фаза A на этом заканчивается). Не нашлась — первый
   запуск: доспроси тип и номер (см. «Разбор аргументов») и продолжай.
3. Установи рабочую область:
   `node "${CONVEYOR_ROOT}/core/scripts/scope.mjs" set --stage create-specification --type <FE|BE|FE-BE> --task <TASK-ID>`
   (для пары — `--type FE-BE --task <TASK-ID FE-задачи>`; запись разрешена в
   systemsAnalysis).
4. Заведи задачу(и) — запиши `meta.json` со скелетом: `schemaVersion: 2`,
   `taskId`, `type`, `title`, `intentId`, `relatedTaskId` (для пары; иначе
   `null`) и пять этапов со `done: false` — `specification` (плюс
   `analysisDone: false`, `specDone: false`), `plan`, `implement-plan`,
   `autotest-plan`, `implement-auto-test`. Каталог
   `tasks/<FE|BE>/<TASK-ID>/` отдельным шагом НЕ создаётся: он появляется при
   записи `meta.json` (Write). `mkdir` по этому пути guard запрещает — в
   папке задачи разрешены только `*.md` и `meta.json`, а подсказка отказа
   говорит про исходники и в этом месте уводит в сторону. У пары FE-BE таких
   каталогов два, правило для обоих одно.
5. Найди рабочую копию анализа (`git-ops locate`) и обнови её
   (`git-ops update --mode write` — фаза ПИШЕТ; грязная рабочая копия →
   остановка с показом статуса). Запиши `analysisBaseSha = mainSha` из
   ответа update — это поле верхнего уровня meta.json, рядом с
   `analysisBranch`.
6. Создай ветку `<INTENT-ID>-analysis` от mainBranch:
   `git-ops branch --path <repo> --branch <INTENT-ID>-analysis --from <mainBranch>`.
   Ветка именуется по INTENT-ID, а не по задаче: у пары FE-BE она ОДНА
   общая. Имя → `meta.json.analysisBranch` (в обеих задачах пары).
   Существующую ветку продолжай; пересоздание — только по подтверждению.
7. Подготовь агенту git-контекст: `git-ops log --path <repo>`.
8. Запусти system-analyst (фаза A): вход — текст `intent.md`, путь к рабочей
   копии анализа, файлы соглашений репозитория (см. `_common.md`, «Запуск
   агента»). Задача — внести требования в документы анализа по ИХ структуре.
   Предварительного согласования правок с пользователем нет. Правки
   точечные: переформатирование документов ЗАПРЕЩЕНО — перевёрстанный файл
   раздувает дифф на весь документ, а по этому диффу работают и ревью
   фазы A, и сборка спецификации в фазе B.
9. Проверь машиночитаемые документы, которые агент тронул (форматы анализа —
   `.adoc`, `.yml`/`.yaml`, `.xml`):
   - есть в репозитории свой линтер или схема (см. файлы соглашений) —
     прогони его по изменённым файлам;
   - линтера нет: `.yml`/`.yaml` и `.xml` Node без зависимостей не разбирает,
     поэтому вынеси проверку синтаксиса отдельным явным пунктом ревьюеру
     (шаг 10) — «на слово» её не засчитывай;
   - в любом случае посмотри `git diff --stat` рабочего дерева: файл,
     переписанный целиком, — признак переформатирования, а не правки.
   При провале — верни агенту на исправление (один раз), затем эскалируй
   пользователю.
10. **Цикл ревью** (`${CONVEYOR_ROOT}/core/stages/_review-loop.md`), домен
    `systems-analysis`: reviewer проверяет НЕзакоммиченные правки анализа
    (`git diff` рабочего дерева), system-analyst отвечает/спорит и
    исправляет. Пара FE-BE: ревью запускается ОДИН раз на общие правки.
    Итог цикла (раунды, исправленное, отклонённое, нерешённое) запиши в
    `meta.json → stages.specification.review` по форме из `_review-loop.md`
    («Запись итога») — на момент ревью артефакта этапа ещё нет, и в раздел
    «Ревью» спецификации итог попадёт в фазе B. Хранить его только в контексте
    сессии НЕЛЬЗЯ: фаза B после обрыва запускается отдельной сессией.
11. Закоммить финальные (после ревью) правки в ветку анализа; сообщение
    коммита содержит INTENT-ID. `git commit` выполняет скилл. Push/MR —
    только по подтверждению пользователя.
12. `meta.json → stages.specification.analysisDone = true` и объект `review`
    (см. `_review-loop.md`); проверь, что `analysisBranch` и
    `analysisBaseSha` записаны. Для пары — в обеих задачах.

## Фаза B — спецификация
13. Смени рабочую область — запись в репозитории больше не нужна:
    `node "${CONVEYOR_ROOT}/core/scripts/scope.mjs" set --stage create-specification --type <FE|BE|FE-BE> --task <TASK-ID> --write none`
    (повторный запуск с `analysisDone:true` начинается прямо отсюда.)
14. Собери дифф собственных правок:
    `git-ops diff --path <repo> --base <analysisBaseSha> --head <analysisBranch>`.
    `<repo>` — путь из `git-ops locate` (шаг 5; на повторном запуске locate
    выполняется, даже когда остальная фаза A пропущена). Головной ref
    реконструировать не нужно: обе границы записаны в meta.json на фазе A.
    Приложи полные версии затронутых документов (для `.adoc` — включая файлы,
    подключённые через `include::`).
15. Запусти system-analyst (фаза B): вход — `intent.md`, дифф, приложенные
    документы, путь к рабочей копии анализа (ТОЛЬКО чтение), итог ревью
    фазы A — читай его ИЗ `meta.json → stages.specification.review`, а не из
    контекста сессии (при продолжении по TASK-ID сессия другая; объекта нет —
    так и скажи агенту, чтобы он написал это в разделе «Ревью», а не выдумывал) —
    и ПОЛНЫЙ текст `core/templates/specification.md`. У задачи,
    продолженной по TASK-ID с пустым `intentId`, intent'а нет: вместо него
    дай легаси-`feature.md` из папки задачи (миграция его сохраняет), а если
    нет и его — требования читаются только из диффа, и это скажи агенту
    прямо. Выход —
    `specification.md` в папке задачи. Пара FE-BE: агент сам разносит
    требования между двумя спецификациями (он только что правил анализ и
    видит, что фронтовое, а что бэковое) и заполняет в каждой раздел
    «Границы задачи»; изменения связанной задачи не превращаются в REQ-ID
    своей — только ссылка на `relatedTaskId`.
16. Валидация:
    `node "${CONVEYOR_ROOT}/core/scripts/validate-artifact.mjs" --file <папка задачи>/specification.md --type specification`
    При `ok:false` — один возврат агенту со списком `missingSections`/
    `problems`, затем покажи пользователю остаток. Непустой `placeholders`
    при `ok:true` — тот же один возврат агенту: в артефакте остался каркас
    шаблона; перечисли ему эти плейсхолдеры, а оставшиеся после возврата
    покажи пользователю. Цикл ревью этого этапа смотрел правки анализа, а не
    текст требований, поэтому другого сигнала «раздел не заполнили» нет.
17. Завершение этапа (см. `_common.md`): `validate-task-folder`, затем
    `meta.json → stages.specification.specDone = true`, `done = true`,
    `baseSha`/`headSha` диффа фазы B. Сними рабочую область
    (`scope.mjs clear`) и покажи сводку: изменённые документы анализа и
    ветка, резюме спецификации, итог ревью, открытые вопросы. Следующий шаг
    — `/conveyor:create-plan`.

## Ошибки
- аргумент не опознан — нет ни `intents/<аргумент>/intent.md`, ни
  `tasks/<FE|BE>/<аргумент>/meta.json` → остановка со списком доступных
  intent'ов и задач с незавершённым этапом `specification`;
- грязная рабочая копия анализа → остановка с показом `git status`;
- запуск по TASK-ID с `analysisDone:true`, но в `meta.json` нет
  `analysisBranch` или `analysisBaseSha` (возможно у задач 1.x) → границы
  диффа взять неоткуда: спроси у пользователя ветку анализа и базовый коммит
  либо предложи путь из последнего пункта — собрать спецификацию по текущему
  состоянию документов;
- релевантные разделы в анализе не нашлись → это не ошибка: агент создаёт
  новый документ/раздел по соглашениям репозитория и отмечает это в таблице
  «Внесённые изменения анализа»;
- дифф фазы B пуст (агент ничего не изменил) → сообщи и предложи собрать
  спецификацию по текущему состоянию документов-источников (с
  подтверждением пользователя).

## DoD
Правки анализа внесены и закоммичены в `<INTENT-ID>-analysis` (коммит — после
ревью); задача(и) созданы, `intentId` проставлен (у задачи, продолженной по
TASK-ID из 1.x, он так и остаётся `null` — intent'а для неё не существует);
`specification.md` заполнен
по шаблону и прошёл валидацию, остатки каркаса (`placeholders`) устранены
либо показаны пользователю; цикл ревью пройден (нерешённые blocker|major
вынесены пользователю); рабочая область снята. Следующий шаг —
`/conveyor:create-plan`.
