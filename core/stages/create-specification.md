# Этап /conveyor:create-specification — правки анализа + спецификация

**Кто запускает:** системный аналитик. **Агент:** system-analyst
(`${CONVEYOR_ROOT}/core/prompts/system-analyst.md`).
**Аргументы:** `INTENT-ID [FE|BE|FE-BE] [номер]`.
**Предусловие:** существует `intents/<INTENT-ID>/intent.md`.

Этап состоит из двух фаз. **Фаза A** — агент вносит требования из intent'а в
документы репозитория системного анализа (единственная фаза конвейера, где
этап пишет в чужой репозиторий). **Фаза B** — по диффу СВОИХ ЖЕ правок
собирается `specification.md`. Между фазами меняется рабочая область.

## Разбор аргументов
- `INTENT-ID` обязателен; не передан — предложи выбор из intent'ов, на
  которые не ссылается ни одна задача (обратный индекс по
  `tasks/*/*/meta.json → intentId`);
- тип (`FE`/`BE`/`FE-BE`) и номер задаёт АНАЛИТИК: в intent'е их нет,
  бизнес-аналитик тип задачи не знает. Чего не передал — спроси ОДНИМ
  объединённым вопросом (тип + номер; номер предложи автоинкрементом:
  максимальный номер по всем `tasks/`, FE и BE вместе, +1);
- `FE-BE` → две связанные задачи в `tasks/FE/` и `tasks/BE/`, каждая со
  своим TASK-ID; в meta.json обеих — `relatedTaskId` и общий `intentId`.
  Переданный номер получает FE-задача, номер BE-задачи предложи
  автоинкрементом в том же вопросе.

**Рабочая область:** репозиторий системного анализа — в фазе A на ЗАПИСЬ, в
фазе B ТОЛЬКО на чтение. Кодовые базы и репозиторий автотестов на этом этапе
не открываются и агенту не сообщаются.

## Идемпотентность (важно — этап дорогой)
Подэтапы фиксируются в `meta.json → stages.specification`: `analysisDone`
(правки анализа внесены, отревьюены и закоммичены) и `specDone`
(спецификация собрана). Повторный запуск:
- `analysisDone:true, specDone:false` → пропусти фазу A целиком, начни с
  фазы B: дифф считается от `analysisBaseSha` до вершины ветки
  `analysisBranch`, правки чужого репозитория НЕ переигрываются;
- обе `true` → спроси «перезаписать / дополнить / отмена» и уточни, что
  именно: только спецификацию или заново и правки анализа.

## Фаза A — правки репозитория анализа
1. Первый шаг — resolve-config (см. `_common.md`): нужна ссылка
   `systemsAnalysis`, её нет в `missingLinks`/`urlLinks` — иначе останови
   этап. Прочитай `intents/<INTENT-ID>/intent.md`.
2. Установи рабочую область:
   `node "${CONVEYOR_ROOT}/core/scripts/scope.mjs" set --stage create-specification --type <FE|BE|FE-BE> --task <TASK-ID>`
   (для пары — `--type FE-BE --task <TASK-ID FE-задачи>`; запись разрешена в
   systemsAnalysis).
3. Создай папку(и) задач и `meta.json` со скелетом: `schemaVersion: 2`,
   `taskId`, `type`, `title`, `intentId`, `relatedTaskId` (для пары; иначе
   `null`) и пять этапов со `done: false` — `specification` (плюс
   `analysisDone: false`, `specDone: false`), `plan`, `implement-plan`,
   `autotest-plan`, `implement-auto-test`.
4. Найди рабочую копию анализа (`git-ops locate`) и обнови её
   (`git-ops update --mode write` — фаза ПИШЕТ; грязная рабочая копия →
   остановка с показом статуса). Запиши `analysisBaseSha = mainSha` из
   ответа update — это поле верхнего уровня meta.json, рядом с
   `analysisBranch`.
5. Создай ветку `<INTENT-ID>-analysis` от mainBranch:
   `git-ops branch --path <repo> --branch <INTENT-ID>-analysis --from <mainBranch>`.
   Ветка именуется по INTENT-ID, а не по задаче: у пары FE-BE она ОДНА
   общая. Имя → `meta.json.analysisBranch` (в обеих задачах пары).
   Существующую ветку продолжай; пересоздание — только по подтверждению.
6. Подготовь агенту git-контекст: `git-ops log --path <repo>`.
7. Запусти system-analyst (фаза A): вход — текст `intent.md`, путь к рабочей
   копии анализа, файлы соглашений репозитория (см. `_common.md`, «Запуск
   агента»). Задача — внести требования в документы анализа по ИХ структуре.
   Предварительного согласования правок с пользователем нет. Правки
   точечные: переформатирование документов ЗАПРЕЩЕНО — перевёрстанный файл
   раздувает дифф на весь документ, а по этому диффу работают и ревью
   фазы A, и сборка спецификации в фазе B.
8. Проверь машиночитаемые документы, которые агент тронул (форматы анализа —
   `.adoc`, `.yml`/`.yaml`, `.xml`):
   - есть в репозитории свой линтер или схема (см. файлы соглашений) —
     прогони его по изменённым файлам;
   - линтера нет: `.yml`/`.yaml` и `.xml` Node без зависимостей не разбирает,
     поэтому вынеси проверку синтаксиса отдельным явным пунктом ревьюеру
     (шаг 9) — «на слово» её не засчитывай;
   - в любом случае посмотри `git diff --stat` рабочего дерева: файл,
     переписанный целиком, — признак переформатирования, а не правки.
   При провале — верни агенту на исправление (один раз), затем эскалируй
   пользователю.
9. **Цикл ревью** (`${CONVEYOR_ROOT}/core/stages/_review-loop.md`), домен
   `systems-analysis`: reviewer проверяет НЕзакоммиченные правки анализа
   (`git diff` рабочего дерева), system-analyst отвечает/спорит и
   исправляет. Пара FE-BE: ревью запускается ОДИН раз на общие правки.
   Итог цикла (раунды, исправленное, отклонённое, нерешённое) сохрани — на
   момент ревью артефакта этапа ещё нет, и в раздел «Ревью» спецификации он
   попадёт в фазе B.
10. Закоммить финальные (после ревью) правки в ветку анализа; сообщение
    коммита содержит INTENT-ID. `git commit` выполняет скилл. Push/MR —
    только по подтверждению пользователя.
11. `meta.json → stages.specification.analysisDone = true` и объект `review`
    (см. `_review-loop.md`); проверь, что `analysisBranch` и
    `analysisBaseSha` записаны. Для пары — в обеих задачах.

## Фаза B — спецификация
12. Смени рабочую область — запись в репозитории больше не нужна:
    `node "${CONVEYOR_ROOT}/core/scripts/scope.mjs" set --stage create-specification --type <FE|BE|FE-BE> --task <TASK-ID> --write none`
13. Собери дифф собственных правок:
    `git-ops diff --path <repo> --base <analysisBaseSha> --head <analysisBranch>`.
    Головной ref реконструировать не нужно: обе границы записаны в meta.json
    на фазе A. Приложи полные версии затронутых документов (для `.adoc` —
    включая файлы, подключённые через `include::`).
14. Запусти system-analyst (фаза B): вход — `intent.md`, дифф, приложенные
    документы, путь к рабочей копии анализа (ТОЛЬКО чтение), итог ревью
    фазы A и ПОЛНЫЙ текст `core/templates/specification.md`. Выход —
    `specification.md` в папке задачи. Пара FE-BE: агент сам разносит
    требования между двумя спецификациями (он только что правил анализ и
    видит, что фронтовое, а что бэковое) и заполняет в каждой раздел
    «Границы задачи»; изменения связанной задачи не превращаются в REQ-ID
    своей — только ссылка на `relatedTaskId`.
15. Валидация:
    `node "${CONVEYOR_ROOT}/core/scripts/validate-artifact.mjs" --file <папка задачи>/specification.md --type specification`
    При `ok:false` — один возврат агенту со списком `missingSections`/
    `problems`, затем покажи пользователю остаток. Непустой `placeholders`
    при `ok:true` — тот же один возврат агенту: в артефакте остался каркас
    шаблона; перечисли ему эти плейсхолдеры, а оставшиеся после возврата
    покажи пользователю. Цикл ревью этого этапа смотрел правки анализа, а не
    текст требований, поэтому другого сигнала «раздел не заполнили» нет.
16. Завершение этапа (см. `_common.md`): `validate-task-folder`, затем
    `meta.json → stages.specification.specDone = true`, `done = true`,
    `baseSha`/`headSha` диффа фазы B. Сними рабочую область
    (`scope.mjs clear`) и покажи сводку: изменённые документы анализа и
    ветка, резюме спецификации, итог ревью, открытые вопросы. Следующий шаг
    — `/conveyor:create-plan`.

## Ошибки
- `intents/<INTENT-ID>/intent.md` не найден → остановка со списком
  доступных intent'ов;
- грязная рабочая копия анализа → остановка с показом `git status`;
- релевантные разделы в анализе не нашлись → это не ошибка: агент создаёт
  новый документ/раздел по соглашениям репозитория и отмечает это в таблице
  «Внесённые изменения анализа»;
- дифф фазы B пуст (агент ничего не изменил) → сообщи и предложи собрать
  спецификацию по текущему состоянию документов-источников (с
  подтверждением пользователя).

## DoD
Правки анализа внесены и закоммичены в `<INTENT-ID>-analysis` (коммит — после
ревью); задача(и) созданы, `intentId` проставлен; `specification.md` заполнен
по шаблону и прошёл валидацию, остатки каркаса (`placeholders`) устранены
либо показаны пользователю; цикл ревью пройден (нерешённые blocker|major
вынесены пользователю); рабочая область снята. Следующий шаг —
`/conveyor:create-plan`.
