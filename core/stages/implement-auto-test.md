# Этап /implement-auto-test — реализация автотестов

**Кто запускает:** тестировщик. **Агент:** qa-autotest-engineer.
**Аргументы:** `TASK-ID`.
**Предусловие:** существует `autotest-plan.md`
(`meta.json → stages['autotest-plan'].done = true`). Завершённость
`implement-plan` НЕ проверяется: автотесты пишутся по плану автотестов
параллельно с разработкой. Готовность реализации нужна только прогону на
стенде — это предусловие следующего этапа, `/conveyor:run-auto-test`.

**Рабочая область:** агент работает СТРОГО по autotest-plan.md и
пишет ТОЛЬКО в репозиторий автотестов (путь — из settings.json:
repos.autoTest.link, через resolve-config) и в артефакты задачи
(report-auto-test.md, колонка «Статус» в autotest-plan.md, meta.json).
Контекст реализации продукта —
ТОЛЬКО autotest-plan.md и specification.md; кодовая база (FE/BE)
на этом этапе не открывается и дифф реализации не готовится — ни агентом,
ни командой. Репозиторий анализа агент тоже не открывает.

## Алгоритм
0. Проверь предусловие по `docs/specs/tasks/<FE|BE>/<TASK-ID>/`: есть
   `autotest-plan.md` и `meta.json → stages['autotest-plan'].done = true`.
   Не выполнено — остановка (см. «Ошибки»), рабочую область не ставь.
1. Установи рабочую область: `scope.mjs set --stage implement-auto-test
   --type <FE|BE> --task <TASK-ID>` (запись — только репозиторий
   автотестов). Для локального пути репозитория автотестов проверь чистоту
   working tree (`git-ops clean-check`).
2. Найди и обнови рабочую копию автотестов (`git-ops locate` +
   `update --mode write`). Создай ветку `<TASK-ID>-autotests` от mainBranch
   (`git-ops branch`); имя → meta.json (`autotestBranch`). Если ветка уже
   есть — продолжай в ней (как в implement-plan, шаг 2).
3. Запусти qa-autotest-engineer: вход — autotest-plan.md,
   specification.md, путь к рабочей копии автотестов; изучить соглашения
   репозитория автотестов; реализовать автотесты из таблицы «Автотесты»
   плана (колонка «Класс» — куда, «Реализация» — что именно там сделать; в
   коде — ID теста из `@TmsLink`), отмечая колонку «Статус» каждой
   выполненной строки прямо в autotest-plan.md (`[ ]` → `[x]`) — как
   разработчик отмечает шаги плана на `/implement-plan`. Остальной текст
   плана агент не правит: расхождение с планом идёт в report-auto-test.md,
   а не переписывает план задним числом. Не хватает данных о реализации —
   агент возвращает запрос на уточнение (вопросы пользователю), а не идёт
   в кодовую базу.
4. Прогон тестов локально — тем же агентом. `report-auto-test.md` на этом
   шаге НЕ пишется: сначала цикл ревью (шаг 5), иначе отчёт переписывался бы
   после каждого исправления.
   Разработка может ещё идти (этап не ждёт `implement-plan`), поэтому часть
   тестов вправе падать просто потому, что функционала ещё нет. Такой тест
   НЕ подгоняется под текущее (старое) поведение продукта — проверка
   остаётся по спецификации, а причина падения помечается «функционал ещё
   не реализован». Подогнанный под старое поведение тест закрепил бы
   расхождение с требованиями вместо того, чтобы его поймать.
5. **Цикл ревью** (`<CONVEYOR_ROOT>/core/stages/_review-loop.md`), домен
   `autotests`. Передай reviewer: autotest-plan.md,
   specification.md и путь к рабочей копии автотестов (для реального
   запуска тестов); путь к кодовой базе НЕ передаётся. reviewer проверяет
   покрытие критериев приёмки, осмысленность кейсов, соответствие
   соглашениям и реальный запуск (падение с причиной «функционал ещё не
   реализован» — не замечание, а ожидаемый результат до выкатки
   реализации); qa-autotest-engineer отвечает/спорит и
   исправляет. Итог цикла — в meta.json (`stages.implement-auto-test.review`);
   в раздел «Ревью» отчёта он попадёт на шаге 6 ИЗ ЭТОГО объекта. Нерешённые
   blocker|major → эскалация пользователю.
6. **Отчёт (без прогона в CI).** Запусти qa-autotest-engineer второй раз:
   вход — autotest-plan.md, результаты локального прогона и объект `review`
   из meta.json (для раздела «Ревью»). Выход — `report-auto-test.md` по
   `core/templates/report-auto-test.md`, заполненный ЦЕЛИКОМ, кроме раздела
   «Прогон в CI»: там агент пишет ссылку на джобу (из настроек) и ветку, а в
   «Сборку» и «Статус» — «ожидается прогон в CI». Сборки ещё не было: её
   запускает отдельный этап `/conveyor:run-auto-test`, и он же допишет
   раздел.
   Отчёт пишется ЗДЕСЬ, а не после сборки, по двум причинам. Сверка с планом
   (ниже) ловит потерянный автотест ДО запуска джобы: `/conveyor:run-auto-test`
   собирает теги из тестов, которые изменила ветка, поэтому потерянный тест —
   это ещё и неполный набор тегов, то есть лишний прогон. И сборка идёт
   долго, не всегда доходит до конца и ждёт выкатки реализации на стенд:
   отчёт, написанный до неё, переживает и обрыв, и недоступный Jenkins —
   тесты написаны и отревьюены, терять этот результат из-за CI нельзя.
   Сразу сверь отчёт с планом:
   `node "<CONVEYOR_ROOT>/core/scripts/validate-artifact.mjs" --file <папка задачи>/report-auto-test.md --type report-auto-test --plan <папка задачи>/autotest-plan.md`
   — количество автотестов в отчёте обязано совпадать с планом: на каждую
   строку таблицы «Автотесты» плана в таблице отчёта есть строка с тем же ID.
   `planMismatch.missing` (тест из плана потерялся) — `ok:false`, один
   автоматический возврат агенту, затем остаток пользователю;
   `planMismatch.extra` (тест сверх плана) — не ошибка, но обязан быть
   объяснён строкой «Расхождение с планом»; нет объяснения — тоже возврат.
   План задним числом не переписывается: расхождение живёт в отчёте.
   `ciPending: true` на этом шаге — норма, так и задумано.
7. Коммит финальных (после ревью) изменений в ветку — только изменения по
   задаче (не `git add -A`; коммитит скилл). Затем спроси пользователя
   (AskUserQuestion), что делать с push: **запушить сейчас** (пушит скилл) /
   **пользователь запушит сам** (дождись его подтверждения, что запушил) /
   **не пушить**. MR — как раньше, по отдельному подтверждению.
8. Обнови meta.json: `stages['implement-auto-test'].done = true` и объект
   `review`. Отчёт закрывается с маркером «ожидается прогон в CI»
   (`ciPending: true`) — это нормальный итог этапа: джобу в Jenkins
   запускает и раздел «Прогон в CI» дописывает `/conveyor:run-auto-test`.
   Сними рабочую область (`scope.mjs clear`). Следующий шаг —
   `/conveyor:run-auto-test`, когда завершён `implement-plan` и функционал
   развёрнут на стенде.

## Ошибки
- `autotest-plan.md` нет или `stages['autotest-plan'].done` не `true` →
  остановка: сначала `/conveyor:create-autotest-plan <TASK-ID>`;
- этап `implement-plan` не завершён → это НЕ ошибка: тесты пишутся
  параллельно с разработкой; падения из-за ещё не реализованного
  функционала помечаются причиной (шаг 4), а не чинятся;
- тестовое окружение недоступно → написать тесты, пометить запуск как
  заблокированный, указать, что нужно для запуска.

## DoD
Все автотесты из таблицы «Автотесты» `autotest-plan.md` реализованы; колонка
«Статус» выполненных строк отмечена (`[x]`), незакрытые строки объяснены в
отчёте; тесты запущены (или блокировка описана);
report-auto-test.md написан после цикла ревью и сошёлся с планом по составу
автотестов (`validate-artifact --type report-auto-test --plan <autotest-plan.md>`:
`ok: true`, `planMismatch.missing` пуст, `extra` объяснён в «Расхождении с
планом»); в разделе «Прогон в CI» — ссылка на джобу, ветка и маркер
«ожидается прогон в CI» (`ciPending: true` — норма для этого этапа);
цикл ревью пройден (коммит — после ревью;
нерешённые blocker|major вынесены пользователю); решение о push принято.
Следующий шаг — `/conveyor:run-auto-test`.
