# Этап /implement-auto-test — реализация автотестов

**Кто запускает:** тестировщик. **Агент:** qa-autotest-engineer.
**Аргументы:** `TASK-ID`.
**Предусловие:** существует `autotest-plan.md`.

**Рабочая область:** агент работает СТРОГО по autotest-plan.md и
пишет ТОЛЬКО в репозиторий автотестов (путь — из settings.json:
repos.autoTest.link, через resolve-config) и в артефакты задачи
(report-auto-test.md, чекбоксы шагов в autotest-plan.md, meta.json).
Контекст реализации продукта —
ТОЛЬКО autotest-plan.md и specification.md; кодовая база (FE/BE)
на этом этапе не открывается и дифф реализации не готовится — ни агентом,
ни командой. Репозиторий анализа агент тоже не открывает.

## Алгоритм
1. Установи рабочую область: `scope.mjs set --stage implement-auto-test
   --type <FE|BE> --task <TASK-ID>` (запись — только репозиторий
   автотестов). Для локального пути репозитория автотестов проверь чистоту
   working tree (`git-ops clean-check`).
2. Найди и обнови рабочую копию автотестов (`git-ops locate` +
   `update --mode write`). Создай ветку `<TASK-ID>-autotests` от mainBranch
   (`git-ops branch`); имя → meta.json (`autotestBranch`). Если ветка уже
   есть — продолжай в ней (как в implement-plan, шаг 2).
3. Запусти qa-autotest-engineer: вход — autotest-plan.md,
   specification.md, путь к рабочей копии автотестов; изучить соглашения
   репозитория автотестов; реализовать автотесты `AT-N` (раздел «Автотесты»
   плана — что писать, «Шаги реализации тестов» — где и в каком порядке; в
   коде — ссылки на ID), отмечая чекбокс каждого
   выполненного шага прямо в autotest-plan.md (`- [ ]` → `- [x]`) — как
   разработчик отмечает шаги плана на `/implement-plan`. Остальной текст
   плана агент не правит: расхождение с планом идёт в report-auto-test.md,
   а не переписывает план задним числом. Не хватает данных о реализации —
   агент возвращает запрос на уточнение (вопросы пользователю), а не идёт
   в кодовую базу.
4. Прогон тестов локально — тем же агентом. `report-auto-test.md` на этом
   шаге НЕ пишется: отчёт формируется в конце этапа (шаг 9), когда известен
   результат прогона в CI. Иначе отчёт пришлось бы переписывать дважды, и
   версия без сборки успевала бы уйти в ревью как окончательная.
5. **Цикл ревью** (`${CONVEYOR_ROOT}/core/stages/_review-loop.md`), домен
   `autotests`. Передай reviewer: autotest-plan.md,
   specification.md и путь к рабочей копии автотестов (для реального
   запуска тестов); путь к кодовой базе НЕ передаётся. reviewer проверяет
   покрытие критериев приёмки, осмысленность кейсов, соответствие
   соглашениям и реальный запуск; qa-autotest-engineer отвечает/спорит и
   исправляет. Итог цикла — в meta.json (`stages.implement-auto-test.review`);
   в раздел «Ревью» отчёта он попадёт на шаге 9 ИЗ ЭТОГО объекта. Нерешённые
   blocker|major → эскалация пользователю.
6. Коммит финальных (после ревью) изменений в ветку — только изменения по
   задаче (не `git add -A`; коммитит скилл). Затем спроси пользователя
   (AskUserQuestion), что делать с push: **запушить сейчас** (пушит скилл) /
   **пользователь запушит сам** (дождись его подтверждения, что запушил) /
   **не пушить**. MR — как раньше, по отдельному подтверждению.
7. **Можно ли запускать джобу.** Ссылка на неё —
   `settings.json → repos.autoTest.linkPipelineAutoTest`, в resolve-config это
   `links.autoTest.pipelineUrl`. Три проверки подряд, и каждая может закончить
   шаг причиной для отчёта (тогда сразу к шагу 9):
   1. ссылки нет в настройках → «джоба не настроена»;
   2. ветка не запушена → «ветка не запушена»: джоба собирает ветку из origin,
      без push прогонится СТАРЫЙ код и отчитается зелёным;
   3. **инструменты.** Имён MCP-инструментов плагин не хранит: у каждой
      команды свой сервер Jenkins. ПОДБЕРИ их сам среди инструментов,
      доступных в этой сессии, — по имени сервера и описанию инструмента
      (Jenkins, CI, build) — и разложи по трём ролям: **запуск сборки с
      параметрами**, **статус сборки**, **результаты тестов сборки**.
      - роль закрыта одним подходящим инструментом — бери его;
      - кандидатов несколько и выбор неочевиден — спроси пользователя
        (AskUserQuestion), каким запускать;
      - инструмента на запуск сборки нет вовсе — джобу **не запускаем**:
        «нет MCP-инструментов для Jenkins». Через Bash (curl, jenkins-cli)
        сборку не запускай: так теряются и разрешение пользователя, и
        параметры джобы;
      - нет инструмента на результаты тестов — не блокер: в отчёт пойдут
        номер сборки, ссылка и статус, а числа прогона — «нет данных».
   Прошли — спроси разрешение на запуск (AskUserQuestion), назвав джобу,
   ветку и то, чем будешь запускать. Отказ — тоже причина для отчёта.
8. **Теги и запуск.** Собери теги из тестов, которые изменила ветка: список
   файлов — `git-ops diff --path <копия> --base <mainBranch> --head <ветка>`
   (либо `git diff --name-only <mainBranch>...<ветка>`), из `*.java`/`*.kt`
   вытащи значения `@Tag("...")`. Покажи получившийся список пользователю и
   спроси: запускать по этим тегам или выбрать другие — список можно
   отредактировать (AskUserQuestion с множественным выбором и своим
   вариантом). В запуск идёт то, что подтвердил пользователь.
   Запусти сборку подобранным на шаге 7 инструментом: джоба — по ссылке из
   настроек, подтверждённые теги — в параметр `TAGS`. Прочие параметры
   джобы (в том числе `TEST_CYCLE`) не передавай: они остаются на умолчаниях
   джобы. Дальше опрашивай статус **раз в 3 минуты**, пока сборка не
   завершится, и забери результаты. Сборка идёт дольше часа — спроси
   пользователя, ждать дальше или писать отчёт со статусом «в процессе».
9. **Отчёт.** Запусти qa-autotest-engineer второй раз: вход — autotest-plan.md,
   результаты локального прогона, объект `review` из meta.json (для раздела
   «Ревью») и факты о сборке: ссылка на джобу, ветка, теги, номер и ссылка на
   сборку, статус, числа прогона. Выход — `report-auto-test.md` по
   `core/templates/report-auto-test.md`. Джобу не запускали — те же входы, но
   в разделе «Прогон в CI»: «джоба с автотестами не запускалась: <причина>».
   Отказ от запуска отчёт НЕ отменяет: тесты написаны, и результат этапа
   должен быть виден.
   Затем сверь отчёт с планом:
   `node "${CONVEYOR_ROOT}/core/scripts/validate-artifact.mjs" --file <папка задачи>/report-auto-test.md --type report-auto-test --plan <папка задачи>/autotest-plan.md`
   — количество автотестов в отчёте обязано совпадать с планом: на каждый
   `AT-N` раздела «Автотесты» плана в таблице отчёта есть строка с тем же ID.
   `planMismatch.missing` (тест из плана потерялся) — `ok:false`, один
   автоматический возврат агенту, затем остаток пользователю;
   `planMismatch.extra` (тест сверх плана) — не ошибка, но обязан быть
   объяснён строкой «Расхождение с планом»; нет объяснения — тоже возврат.
   План задним числом не переписывается: расхождение живёт в отчёте.
   Числа прогона в CI в «Итог прогона» не переносятся: сборка идёт по тегам и
   шире задачи.
10. Обнови meta.json: `stages['implement-auto-test'].done = true`, объект
    `review` и — рядом с `autotestBranch` — `autoTestJob`:
    `{ "url": "<ссылка на сборку>", "status": "<статус как вернул Jenkins: SUCCESS|UNSTABLE|FAILURE|ABORTED|… — либо «в процессе»>" }`.
    Джобу не запускали — `{ "url": null, "status": "не запускалась: <причина>" }`.
    Двух полей достаточно: остальное (джоба, ветка, теги, чем запускали)
    либо уже есть в meta.json, либо живёт в разделе «Прогон в CI» отчёта, и
    дублировать это в meta.json незачем. Как и `review`, поле относится к
    ПОСЛЕДНЕМУ прогону (перезапись, не накопление).
    Сними рабочую область (`scope.mjs clear`).

## Ошибки
- тестовое окружение недоступно → написать тесты, пометить запуск как
  заблокированный, указать, что нужно для запуска;
- MCP-инструментов для Jenkins в сессии нет, сервер не отвечает, джоба
  недоступна, нет прав на запуск →
  этап НЕ падает: причина идёт в раздел «Прогон в CI», отчёт формируется,
  этап завершается. Тесты написаны и закоммичены — терять этот результат
  из-за недоступного CI нельзя;
- сборка упала (FAILURE/UNSTABLE) → это результат, а не ошибка этапа: статус
  и ссылка идут в отчёт, разбор падений — отдельная работа.

## DoD
Все кейсы P1 из `autotest-plan.md` реализованы; чекбоксы выполненных шагов
в нём отмечены (`- [x]`), незакрытые шаги объяснены в отчёте; тесты
запущены (или блокировка описана);
report-auto-test.md сформирован ПОСЛЕ прогона в CI и сошёлся с планом по
составу автотестов
(`validate-artifact --type report-auto-test --plan <autotest-plan.md>`:
`planMismatch.missing` пуст, `extra` объяснён в «Расхождении с планом»);
в разделе «Прогон в CI» — либо номер и статус сборки, либо причина, почему
джоба не запускалась; в meta.json записан `autoTestJob` (ссылка и статус);
цикл ревью пройден (коммит — после ревью;
нерешённые blocker|major вынесены пользователю). Конвейер задачи завершён.
