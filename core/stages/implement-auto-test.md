# Этап /implement-auto-test — реализация автотестов

**Кто запускает:** тестировщик. **Агент:** qa-autotest-engineer.
**Аргументы:** `TASK-ID`.
**Предусловие:** существует `autotest-plan.md`
(`meta.json → stages['autotest-plan'].done = true`). Завершённость
`implement-plan` НЕ проверяется: автотесты пишутся по плану автотестов
параллельно с разработкой. Готовность реализации нужна только прогону на
стенде — это предусловие этапа `/conveyor:run-auto-test`.

**Тесты на этом этапе НЕ запускаются, отчёт о прогоне НЕ пишется.** Разработка
ещё идёт, и запуск до выкатки функционала показывает в основном то, что его
нет; окружение для запуска есть не у всех. Прогон и `report-auto-test.md` —
дело `/conveyor:run-auto-test`, когда функционал на стенде. Написанный код
здесь проверяют три вещи: сборка тестового кода без запуска тестов (шаг 3),
цикл ревью (шаг 4) и сверка плана с кодом (шаг 5).

**Рабочая область:** агент работает СТРОГО по autotest-plan.md и
пишет ТОЛЬКО в репозиторий автотестов (путь — из settings.json:
repos.autoTest.link, через resolve-config) и в артефакты задачи
(колонка «Статус» в autotest-plan.md, meta.json).
Контекст реализации продукта —
ТОЛЬКО autotest-plan.md и specification.md; кодовая база (FE/BE)
на этом этапе не открывается и дифф реализации не готовится — ни агентом,
ни командой. Репозиторий анализа агент тоже не открывает.

## Алгоритм
0. Проверь предусловие по `docs/specs/tasks/<FE|BE>/<TASK-ID>/`: есть
   `autotest-plan.md` и `meta.json → stages['autotest-plan'].done = true`.
   Не выполнено — остановка (см. «Ошибки»), рабочую область не ставь.
1. Установи рабочую область: `scope.mjs set --stage implement-auto-test
   --type <FE|BE> --task <TASK-ID>` (запись — только репозиторий
   автотестов). Для локального пути репозитория автотестов проверь чистоту
   working tree (`git-ops clean-check`).
2. Найди и обнови рабочую копию автотестов (`git-ops locate` +
   `update --mode write`). Создай ветку `<TASK-ID>-autotests` от mainBranch
   (`git-ops branch`); имя → meta.json (`autotestBranch`). Если ветка уже
   есть — продолжай в ней (как в implement-plan, шаг 2).
3. **Реализация и сборка.** Запусти qa-autotest-engineer: вход —
   autotest-plan.md, specification.md, путь к рабочей копии автотестов;
   изучить соглашения
   репозитория автотестов; реализовать автотесты из таблицы «Автотесты»
   плана (колонка «Класс» — куда, «Реализация» — что именно там сделать; в
   коде — ID теста из `@TmsLink`), отмечая колонку «Статус» каждой
   выполненной строки прямо в autotest-plan.md (`[ ]` → `[x]`) — как
   разработчик отмечает шаги плана на `/implement-plan`. Остальной текст
   плана агент не правит: расхождение с планом он ВОЗВРАЩАЕТ скиллу, а не
   переписывает план задним числом. Не хватает данных о реализации —
   агент возвращает запрос на уточнение (вопросы пользователю), а не идёт
   в кодовую базу.
   Затем агент **собирает тестовый код без запуска тестов** — командой из
   соглашений репозитория автотестов (компиляция тестов: `mvn test-compile`,
   `gradle testClasses` и подобные). Ошибки сборки он чинит. Сами тесты не
   запускает: тест проверяет спецификацию, а функционала на стенде может ещё
   не быть — подгонять тест под текущее (старое) поведение продукта нельзя,
   он закрепил бы расхождение с требованиями вместо того, чтобы его поймать.
   Агент возвращает два факта, и скилл пишет их в
   `meta.json → stages['implement-auto-test']`:
   - `build` — `{ "status": "ok" | "failed" | "blocked", "command": "<чем собирали>", "note": "<причина, если не ok>" }`.
     `blocked` — собрать не удалось по причине вне кода тестов (нет
     зависимостей, сети, инструмента сборки): этап не падает, причина
     идёт в итоговую сводку;
   - `deviations` — расхождения с планом, объект «ID теста → причина»:
     строка плана не реализована (осталась `[ ]`) либо написан тест сверх
     плана. Расхождений нет — пустой объект. Из него `/conveyor:run-auto-test`
     возьмёт строку «Расхождение с планом» отчёта. Объект относится к
     ПОСЛЕДНЕМУ прогону этапа: при повторном запуске собери его заново, а
     не дописывай к прежнему — иначе в отчёт уйдут причины расхождений,
     которых уже нет.
4. **Цикл ревью** (`<CONVEYOR_ROOT>/core/stages/_review-loop.md`), домен
   `autotests`. Передай reviewer: autotest-plan.md,
   specification.md и путь к рабочей копии автотестов (чтобы собрать
   тестовый код); путь к кодовой базе НЕ передаётся. reviewer проверяет
   покрытие критериев приёмки, осмысленность кейсов, соответствие
   соглашениям и то, что тестовый код собирается; тесты он не запускает —
   по той же причине, что и агент. qa-autotest-engineer отвечает/спорит и
   исправляет, после правок пересобирает тестовый код (обнови `build`).
   Итог цикла — в meta.json (`stages.implement-auto-test.review`): раздела
   «Ревью» на этом этапе писать некуда, в отчёт он попадёт ИЗ ЭТОГО объекта
   на `/conveyor:run-auto-test`. Нерешённые blocker|major → эскалация
   пользователю.
5. **Сверка плана с кодом.** Проверяется то, что лежит в рабочей копии, а не
   рассказ агента:
   `node "<CONVEYOR_ROOT>/core/scripts/tms-cases.mjs" coverage --task <абс. путь к папке задачи> --repo <копия автотестов> --base <mainBranch>`
   Скрипт ничего не пишет. В ответе:
   - `missing` — ID из таблицы «Автотесты» плана, которого нет в коде: тест
     не написан;
   - `unticked` — строка плана без `[x]`;
   - `untouched` — тест в коде есть, но ветка не тронула ни одного файла с
     ним, хотя «Реализация» плана велела его создать или изменить. Наличие
     ID тут ничего не доказывает: тест был в коде и до ветки. Строки
     «переиспользуется без правок: только прогон» сюда не попадают — им
     менять нечего;
   - `extra` — тесты сверх плана: `@TmsLink`, которых не было до ветки и нет
     в плане (перенос и переформатирование существующего теста не
     считаются). `placeholder: true` — у такого теста заглушка
     `PROJ-T999-N`, а кейс в Zephyr `/conveyor:update-tms` заводит только по
     таблице плана: кейса у него не будет, и результаты сборки с кейсом не
     свяжутся. Скажи об этом пользователю: либо тест вносится в план
     (повтор `/conveyor:create-autotest-plan` → «дополнить» — тогда он
     перестаёт быть «сверх плана»), либо остаётся без кейса — это решение
     идёт причиной в `deviations`;
   - `unexplained` — расхождения, у которых нет причины в `deviations`;
   - `staleDeviations` — ключи `deviations`, за которыми расхождения уже
     нет (тест дописали, строку отметили);
   - `problems` — сверку не удалось выполнить целиком (например, не найдена
     общая точка с `<mainBranch>`).
   `ok:false` с непустым `unexplained` — один автоматический возврат агенту
   со списком: дописать тест, отметить «Статус» либо назвать причину. Причины
   допиши в `deviations` и повтори сверку; остаток покажи пользователю — он
   решает, принять расхождение (причина с его слов идёт в `deviations`) или
   остановить этап. План задним числом не переписывается.
   `ok:false` с непустым `problems` — это НЕ расхождение, агенту его не
   возвращай: устрани причину (обнови основную ветку, проверь `mainBranch`)
   и повтори; не получается — остановка и вопрос пользователю. Непроверенную
   сверку зелёной не считай.
   Перед тем как идти дальше, убери из `deviations` ключи из
   `staleDeviations`.
   Сверка стоит ДО коммита и push не случайно: `/conveyor:run-auto-test`
   собирает теги из тестов, которые изменила ветка, поэтому потерянный тест —
   это ещё и неполный набор тегов, то есть лишний прогон джобы.
6. Коммит финальных (после ревью и сверки) изменений в ветку — только
   изменения по задаче (не `git add -A`; коммитит скилл). Затем спроси
   пользователя (AskUserQuestion), что делать с push: **запушить сейчас**
   (пушит скилл) / **пользователь запушит сам** (дождись его подтверждения,
   что запушил) / **не пушить**. MR — как раньше, по отдельному подтверждению.
7. Завершение этапа (см. `_common.md`): `validate-task-folder`, затем
   meta.json: `stages['implement-auto-test'].done = true` рядом с `build`,
   `deviations` и `review`. Сними рабочую область (`scope.mjs clear`).
   Напечатай сводку: сколько автотестов по плану и сколько реализовано
   (`planned` / `implemented` из сверки), расхождения с причинами, итог
   сборки тестового кода. Следующий шаг —
   `/conveyor:update-tms`: кейсы новых тестов заводятся в Zephyr, и
   заглушки `PROJ-T999-N` в `@TmsLink` меняются на их ключи. После него —
   `/conveyor:run-auto-test`, когда завершён `implement-plan` и функционал
   развёрнут на стенде: он прогонит тесты и напишет `report-auto-test.md`.

## Ошибки
- `autotest-plan.md` нет или `stages['autotest-plan'].done` не `true` →
  остановка: сначала `/conveyor:create-autotest-plan <TASK-ID>`;
- этап `implement-plan` не завершён → это НЕ ошибка: тесты пишутся
  параллельно с разработкой и на этом этапе не запускаются;
- тестовый код не собирается, и агент не может это исправить → это
  blocker: покажи ошибку сборки пользователю, этап не закрывай
  (`build.status = "failed"`);
- собрать нечем или не из чего (нет зависимостей, сети, инструмента
  сборки) → `build.status = "blocked"` с причиной; этап завершается, первая
  же сборка в Jenkins покажет то, что не удалось проверить здесь;
- сверка плана с кодом не сошлась и после возврата агенту → остаток
  пользователю (см. шаг 5), молча этап не закрывай.

## DoD
Все автотесты из таблицы «Автотесты» `autotest-plan.md` реализованы; колонка
«Статус» выполненных строк отмечена (`[x]`); тестовый код собран без запуска
тестов (`build` в meta.json: `ok` либо `blocked` с причиной);
цикл ревью пройден (коммит — после ревью; нерешённые blocker|major вынесены
пользователю); сверка плана с кодом зелёная (`tms-cases.mjs coverage`:
`ok: true` — `unexplained` пуст, каждое расхождение записано в `deviations`
с причиной); решение о push принято; рабочая область снята.
`report-auto-test.md` на этом этапе НЕ создаётся.
Следующий шаг — `/conveyor:update-tms` (кейсы в Zephyr), затем
`/conveyor:run-auto-test` (прогон на стенде и отчёт).
