# Этап /implement-plan — реализация

**Кто запускает:** разработчик. **Агент:** frontend-developer или
backend-developer (по типу задачи).
**Аргументы:** `TASK-ID`. **Предусловие:** существует `plan.md`.

**Рабочая область:** ТОЛЬКО кодовая база по типу задачи (repos.frontend
или repos.backend) + артефакты задачи (plan.md, meta.json). Репозиторий
анализа, автотестов и чужая кодовая база не открываются и агенту не
сообщаются. Путь к нужной кодовой базе бери из settings.json через
resolve-config (repos.<тип>.link), не спрашивая и не угадывая.

## Алгоритм
1. Установи рабочую область: `scope.mjs set --stage implement-plan --type
   <FE|BE> --task <TASK-ID>`. Для локального пути кодовой базы проверь
   чистоту working tree (`git-ops clean-check`); грязная → остановка с
   показом состояния.
2. Обнови рабочую копию (`git-ops update --mode write`). Создай ветку
   `<TASK-ID>-<slug>` от mainBranch (`git-ops branch`). Slug — перевод или
   транслитерация title в kebab-case латиницей, до 30 символов; сгенерируй и
   дай пользователю изменить. Запиши имя в meta.json (`implementBranch`).
   Повторный запуск: если implementBranch записана и ветка есть —
   переключись на неё и продолжай; пересоздание от mainBranch — только по
   явному подтверждению с предупреждением о потере коммитов.
3. Запусти агента-разработчика: реализация строго по шагам plan.md; после
   каждого шага — отметка чекбокса в plan.md.
4. Прогон линтеров и тестов проекта (агент). Падение → чинить до зелёного
   либо честно зафиксировать в plan.md (раздел «Отклонения и остатки»).
5. **Цикл ревью** (`${CONVEYOR_ROOT}/core/stages/_review-loop.md`), домен
   `frontend` или `backend` (по типу задачи): reviewer проверяет код
   (корректность, покрытие REQ-ID, соглашения, безопасность, зелёные
   тесты/линтеры), разработчик отвечает/спорит и исправляет. Итог — в разделе
   «Ревью» plan.md; нерешённые blocker|major → эскалация пользователю.
6. Закоммить финальные (после ревью) изменения в ветку задачи. Коммить
   ТОЛЬКО изменения по задаче (явный набор путей, не `git add -A`) — чтобы не
   вкоммитить наведённые прогоном тестов файлы (снапшоты, покрытие, lock).
   Сообщения коммитов начинаются с TASK-ID; коммитит скилл. Push и создание
   MR — только по явному подтверждению пользователя (плюс permission-prompt
   guard-хука).
7. Обнови meta.json (`stages.implement-plan.done = true`, объект `review`).
   Сними рабочую область (`scope.mjs clear`). Итог — в plan.md (шаги,
   «Отклонения и остатки», «Ревью») и в финальном сообщении: что сделано,
   результаты тестов/линтеров, итог ревью, список коммитов, что осталось.

## Ошибки
Конфликт / грязная рабочая копия → остановиться и показать состояние, ничего
не затирая.

## DoD
Все шаги плана отмечены; отклонения и остатки внесены в plan.md; тесты и
линтеры зелёные; цикл ревью пройден (коммит — после ревью; нерешённые
blocker|major вынесены пользователю); ветка с коммитами существует. Следующий
шаг — `/create-requirements-auto-test`.
