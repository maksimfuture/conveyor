# Этап /implement-plan — реализация

**Кто запускает:** разработчик. **Агент:** frontend-developer или
backend-developer (по типу задачи).
**Аргументы:** `TASK-ID`. **Предусловие:** существует `plan.md`.

**Рабочая область:** кодовая база по типу задачи + артефакты задачи (plan.md,
meta.json). Репозиторий анализа, автотестов и чужая кодовая база не
открываются и агенту не сообщаются. Пути бери из resolve-config (`units`,
`codebase.<тип>`), не спрашивая и не угадывая.
ИСХОДНИКИ — ТОЛЬКО в рабочую копию кодовой базы. В папке задачи разрешены
лишь артефакты (`*.md`, `meta.json`); файл кода в `tasks/` — ошибка,
guard такую запись блокирует.

**Писать можно только туда, где обещал план.** Область записи — не «вся
кодовая база», а список репозиториев из раздела «Затронутые репозитории»
plan.md. У BE-задачи их обычно несколько (`backend.core`, `backend.api`,
`backend.common`, `backend.config`), и этап проходит по КАЖДОМУ: заводит
ветку, правит код, коммитит.

## Алгоритм
1. Возьми список репозиториев из плана:
   `node "<CONVEYOR_ROOT>/core/scripts/plan-repos.mjs" --file <папка задачи>/plan.md --workspace <workspaceRoot> --type <FE|BE>`
   При `ok:false` — ОСТАНОВКА с текстом `problems`: план не говорит, где
   править (нет раздела, шаги без тега, таблица разошлась с шагами,
   несуществующий id, репозиторий чужой кодовой базы). Это лечится возвратом
   на `/create-plan`, а не догадкой.
   Сверься с `meta.json → stages.plan.repos`: расхождение значит, что plan.md
   правили руками после планирования — скажи об этом пользователю и спроси,
   продолжать ли.
   `scope.mjs` тот же список проверяет ещё раз и права ЗА пределы кодовой базы
   этапа не выдаст: область — это пересечение плана и того, что этапу вообще
   разрешено. Отказ «репозитории вне кодовой базы этапа» означает, что план
   назвал чужой репозиторий, а не что область сломалась.
2. Установи рабочую область по этому списку:
   `scope.mjs set --stage implement-plan --type <FE|BE> --task <TASK-ID> --write <repos через запятую>`
3. Для КАЖДОГО репозитория из списка проверь чистоту working tree
   (`git-ops clean-check`). Грязная хотя бы одна → остановка с показом
   состояния, ДО единой правки: иначе задача останется наполовину заведённой
   в части репозиториев.
4. Для КАЖДОГО репозитория: обнови (`git-ops update --mode write`) и создай
   ветку `<TASK-ID>-<slug>` от его `mainBranch` (`git-ops branch`). Slug —
   перевод или транслитерация title в kebab-case латиницей, до 30 символов;
   сгенерируй ОДИН на задачу и дай пользователю изменить: имя ветки во всех
   репозиториях одинаковое — по нему задача собирается из любого из них.
   Запиши в meta.json:
   ```json
   "implementBranches": {
     "backend.api": { "branch": "TASK-165-tags", "baseSha": "<mainSha>" }
   }
   ```
   Повторный запуск: если `implementBranches` записан и ветки есть —
   переключись на них и продолжай; пересоздание от mainBranch — только по
   явному подтверждению с предупреждением о потере коммитов. Задачи, заведённые
   до перехода на несколько репозиториев, хранят строку `implementBranch` —
   читай и её.
5. Запусти агента-разработчика: реализация строго по шагам plan.md; тег
   `Репозиторий:` у шага говорит, в какую рабочую копию писать. Передай ему
   пути ТОЛЬКО тех репозиториев, что в плане. После каждого шага — отметка
   чекбокса в plan.md.
6. **Понадобился репозиторий вне плана.** Агент туда НЕ идёт (guard всё равно
   не пустит), а возвращает запрос на уточнение. Тогда:
   - спроси пользователя через AskUserQuestion: добавить репозиторий в план и
     продолжить / решить иначе в рамках плана / остановить этап;
   - при согласии допиши строку в «Затронутые репозитории» и шаг(и) в «Шаги
     реализации», отметь это в «Отклонения и остатки», подготовь новый
     репозиторий (шаги 3-4 для него) и перевыставь область
     (`scope.mjs set … --write <новый список>`);
   - перезапусти агента с ответом. Без явного согласия пользователя область не
     расширяется.
7. Прогон линтеров и тестов проекта (агент) — в КАЖДОМ затронутом
   репозитории. Падение → чинить до зелёного либо честно зафиксировать в
   plan.md (раздел «Отклонения и остатки») с указанием репозитория:
   «зелёные тесты в трёх репозиториях из четырёх» — это не зелёные тесты.
8. **Цикл ревью** (`<CONVEYOR_ROOT>/core/stages/_review-loop.md`), домен
   `frontend` или `backend` (по типу задачи): reviewer проверяет код
   (корректность, покрытие REQ-ID, соглашения, безопасность, зелёные
   тесты/линтеры). Ревью ОДНО на задачу, дифф — объединённый по всем
   затронутым репозиториям с разметкой `### Репозиторий <id>`: рассогласование
   между `api`, `core` и `common` видно только на общем диффе. Разработчик
   отвечает/спорит и исправляет. Итог — в разделе «Ревью» plan.md;
   нерешённые blocker|major → эскалация пользователю.
9. Закоммить финальные (после ревью) изменения в ветку задачи — в каждом
   затронутом репозитории. Коммить ТОЛЬКО изменения по задаче (явный набор
   путей, не `git add -A`) — чтобы не вкоммитить наведённые прогоном тестов
   файлы (снапшоты, покрытие, lock). Сообщения коммитов начинаются с TASK-ID;
   коммитит скилл. Push и создание MR — только по явному подтверждению
   пользователя (плюс permission-prompt guard-хука), в ПОРЯДКЕ МЕРЖА из
   плана. Отказ от push в одном репозитории не отменяет остальные — скажи об
   этом явно.
10. Проверь чистоту папки задачи (`validate-task-folder.mjs --task <путь>`,
    см. _common.md «Завершение этапа»): исходники, оказавшиеся в `tasks/`,
    перенеси в рабочую копию кодовой базы. Затем обнови meta.json
    (`stages.implement-plan.done = true`, объект `review`, `implementBranches`
    с `headSha` каждой ветки).
    Сними рабочую область (`scope.mjs clear`). Итог — в plan.md (шаги,
    «Отклонения и остатки», «Ревью») и в финальном сообщении ТАБЛИЦЕЙ:
    репозиторий → ветка → коммиты → что дальше (push/MR сделан или нет),
    плюс результаты тестов/линтеров, итог ревью и что осталось.

## Ошибки
Конфликт / грязная рабочая копия → остановиться и показать состояние, ничего
не затирая; называй КОНКРЕТНЫЙ репозиторий. Отказ guard'а «рабочая копия вне
рабочей области» означает, что план этот репозиторий не объявлял — см. шаг 6,
а не «guard сломался».

## DoD
Все шаги плана отмечены; отклонения и остатки внесены в plan.md; тесты и
линтеры зелёные во ВСЕХ затронутых репозиториях; цикл ревью пройден (коммит —
после ревью; нерешённые blocker|major вынесены пользователю); в каждом
затронутом репозитории есть ветка с коммитами, и она записана в
`implementBranches`. Следующий шаг — `/conveyor:create-autotest-plan`.
