# Этап /conveyor:intent — сформировать намерение (БА)

**Кто запускает:** бизнес-аналитик. **Агент:** business-analyst
(`<CONVEYOR_ROOT>/core/prompts/business-analyst.md`).
**Аргументы:** `[INTENT-ID] [описание/пожелание]` — оба опциональны.

Суть: превратить пожелание заказчика в `intents/<INTENT-ID>/intent.md`.
Режим репозитория бизнес-анализа задаёт
`settings.json → repos.businessAnalysis.update`: при `false` он только
читается, при `true` агент обновляет документы бизнес-анализа в отдельной
ветке и создаёт MR. Репозиторий системного анализа на этом этапе не
открывается — с ним работает системный аналитик на следующем этапе.

**Исключения из `_common.md`:** разделы «Определение задачи» и «Завершение
этапа» к этому этапу не применяются — ни задач, ни `meta.json`, ни папки
задачи (а с ней и `validate-task-folder`) у intent'а нет; идентификатор
`INTENT-N` и завершение этапа описаны здесь. Остальные разделы общих правил
действуют.

## Разбор аргументов
- первый токен вида `INTENT-<N>` — идентификатор; остальное — описание;
- ID не передан → предложи автоинкремент: максимальный номер по папкам
  `intents/INTENT-*` + 1; пользователь может задать свой;
- описание не передано → спроси одним вопросом, что нужно сделать.

**Рабочая область:** репозиторий бизнес-анализа; запись в него разрешена
только при `repos.businessAnalysis.update: true`. `intent.md` всегда пишется
в `intents/<INTENT-ID>/`. Кодовые базы и репозиторий автотестов не
открываются и агенту не сообщаются.

## Алгоритм
1. Первый шаг — resolve-config (см. `_common.md`). Нужна ссылка
   `businessAnalysis`; её нет в `missingLinks`/`urlLinks`, а путь ведёт внутрь
   workspace — иначе останови этап.
2. Прочитай `links.businessAnalysis.update` из результата resolve-config и
   установи рабочую область:
   - `false` → `scope.mjs set --stage intent --task <INTENT-ID> --write none`;
   - `true` → `scope.mjs set --stage intent --task <INTENT-ID> --write businessAnalysis`.
   Значение иного типа — ошибка конфигурации, этап останови.
   `--type` здесь НЕ передаётся: типа задачи у intent нет, FE/BE решает
   системный аналитик на спецификации; scope.mjs отвергнет `--type`.
3. Найди рабочую копию бизнес-анализа (`git-ops locate`) и обнови её:
   - `update:false` → `git-ops update --mode read`; грязная копия не является
     ошибкой, только предупреждение;
   - `update:true` → сначала `git-ops clean-check`. Ожидаемая ветка —
     `<INTENT-ID>-business-analysis`. Если копия грязная И текущая ветка
     ожидаемая, покажи status и спроси, принадлежат ли изменения прерванному
     запуску этого intent'а: «продолжить / остановиться». При «продолжить» не
     вызывай update и branch, сохрани существующий diff и переходи к шагу 4.
     Если ветка другая либо пользователь не подтвердил принадлежность правок —
     останови этап. Если копия чистая, выполни `git-ops update --mode write`,
     затем создай/продолжи ожидаемую ветку от `mainBranch` через `git-ops
     branch`. Существующую ветку не пересоздавай.
4. Идемпотентность: если `intents/<INTENT-ID>/intent.md` уже есть —
   предложи «дополнить / перезаписать / отмена». Если на этот intent уже
   ссылается задача (`docs/specs/tasks/*/*/meta.json → intentId`), предупреди
   об этом до выбора: правка intent'а не меняет уже созданную спецификацию.
5. Запусти business-analyst: вход — описание из промпта, путь к рабочей
   копии бизнес-анализа и режим `update`, путь к папке intent'а, ПОЛНЫЙ текст
   шаблона `core/templates/intent.md`, файлы соглашений репозитория анализа
   (см. `_common.md`, «Запуск агента»). Выход — заполненный `intent.md`.
   При `update:true` агент также вносит точечные изменения в документы
   бизнес-анализа по их существующей структуре; при `false` репозиторий не
   правит. Каталог `intents/<INTENT-ID>/` отдельным шагом НЕ создаётся: он появляется
   при записи `intent.md` (Write). `mkdir` по этому пути guard запрещает — в
   папке артефактов разрешены только `*.md` и `meta.json`.
6. Агент вернул запрос на уточнение — задай вопросы пользователю через
   AskUserQuestion и перезапусти его с ответами (см. `_common.md`).
7. Валидация:
   `node "<CONVEYOR_ROOT>/core/scripts/validate-artifact.mjs" --file
   intents/<INTENT-ID>/intent.md --type intent`
   При `ok:false` — один возврат агенту со списком `missingSections`/
   `problems` и повторная валидация. Если повторно `ok:false`, покажи
   пользователю остаток, сними scope и ОСТАНОВИ этап: к ревью, commit, push и
   MR переходить запрещено. Непустой `placeholders`
   при `ok:true` — тот же один возврат агенту: в артефакте остался каркас
   шаблона; перечисли ему эти плейсхолдеры, а оставшиеся после возврата
   покажи пользователю.
8. При `update:true` проверь diff и машиночитаемые файлы по правилам
   репозитория, затем запусти цикл ревью из `_review-loop.md` с доменом
   `business-analysis`, source-of-truth = созданный `intent.md`. После
   успешного ревью выполни только через git-ops:
   - `git-ops commit --path <repo> --branch <INTENT-ID>-business-analysis
     --main <mainBranch> --message "<INTENT-ID>: update business analysis"`;
   - `git-ops push --path <repo> --branch <INTENT-ID>-business-analysis
     --main <mainBranch> --create-mr --title "<INTENT-ID>: business analysis"`.
   `--create-mr` использует GitLab push option и создаёт MR в `mainBranch`;
   обычные `git commit`/`git push` напрямую не вызывай. Ошибка commit, push
   или создания MR останавливает этап; сообщи сохранённую локальную ветку и
   вывод git-ops.
9. Сними рабочую область (`scope.mjs clear`). Покажи резюме intent'а,
   открытые вопросы и следующий шаг:
   `/conveyor:create-specification <INTENT-ID> <FE|BE|FE-BE> [номер]`.

## Ревью
При `update:false` цикл ревью не запускается: качество intent проверяется
валидацией шаблона и вопросами пользователю. При `update:true` ревьюятся
незакоммиченные изменения репозитория бизнес-анализа.

## Ошибки
- рабочая копия бизнес-анализа не найдена → остановка с подсказкой склонировать её
  в путь из `settings.json` (плагин не клонирует);
- текущий процесс в анализе не описан → это не ошибка: агент описывает
  «Процесс AS IS» по описанию из промпта и добавляет в «Открытые вопросы»
  пункт «В анализе не найдено: …». По этой метке системный аналитик на
  спецификации отличает «документа нет» от «не нашёл по названию».
- незакоммиченный diff на ожидаемой ветке после обрыва можно продолжить только
  после явного подтверждения пользователя; чужой diff и другая ветка не
  присваиваются текущему запуску;
- повторная неуспешная валидация intent.md блокирует публикацию.

## DoD
`intents/<INTENT-ID>/intent.md` создан и прошёл валидацию шаблона; остатки
каркаса шаблона (`placeholders`) устранены либо показаны пользователю. При
`update:true` правки бизнес-анализа прошли ревью, закоммичены, запушены и MR
создан. Рабочая область снята; пользователю показаны открытые вопросы и
следующий шаг.
