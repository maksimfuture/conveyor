# Этап /conveyor:intent — сформировать намерение (БА)

**Кто запускает:** бизнес-аналитик. **Агент:** business-analyst
(`${CONVEYOR_ROOT}/core/prompts/business-analyst.md`).
**Аргументы:** `[INTENT-ID] [описание/пожелание]` — оба опциональны.

Суть: превратить пожелание заказчика в `intents/<INTENT-ID>/intent.md`.
Репозиторий системного анализа читается, но НЕ правится — правки внесёт
системный аналитик на следующем этапе.

**Исключения из `_common.md`:** разделы «Определение задачи» и «Завершение
этапа» к этому этапу не применяются — ни задач, ни `meta.json`, ни папки
задачи (а с ней и `validate-task-folder`) у intent'а нет; идентификатор
`INTENT-N` и завершение этапа описаны здесь. Остальные разделы общих правил
действуют.

## Разбор аргументов
- первый токен вида `INTENT-<N>` — идентификатор; остальное — описание;
- ID не передан → предложи автоинкремент: максимальный номер по папкам
  `intents/INTENT-*` + 1; пользователь может задать свой;
- описание не передано → спроси одним вопросом, что нужно сделать.

**Рабочая область:** репозиторий системного анализа — ТОЛЬКО ЧТЕНИЕ;
запись — только `intents/<INTENT-ID>/`. Кодовые базы и репозиторий
автотестов не открываются и агенту не сообщаются.

## Алгоритм
1. Первый шаг — resolve-config (см. `_common.md`). Нужна ссылка
   `systemsAnalysis`; её нет в `missingLinks` — иначе останови этап.
2. Установи рабочую область:
   `scope.mjs set --stage intent --task <INTENT-ID>`
   (запись в репозитории запрещена — `stageWriteRepoKeys` для intent пуст).
   `--type` здесь НЕ передаётся: типа задачи у intent нет, FE/BE решает
   системный аналитик на спецификации; scope.mjs отвергнет `--type`.
3. Найди рабочую копию анализа (`git-ops locate`) и обнови её
   (`git-ops update --mode read` — этап только читает; грязная копия здесь
   НЕ является ошибкой, просто предупреждение).
4. Идемпотентность: если `intents/<INTENT-ID>/intent.md` уже есть —
   предложи «дополнить / перезаписать / отмена». Если на этот intent уже
   ссылается задача (`tasks/*/*/meta.json → intentId`), предупреди об этом
   до выбора: правка intent'а не меняет уже созданную спецификацию.
5. Запусти business-analyst: вход — описание из промпта, путь к рабочей
   копии анализа (только чтение), путь к папке intent'а, ПОЛНЫЙ текст
   шаблона `core/templates/intent.md`, файлы соглашений репозитория анализа
   (см. `_common.md`, «Запуск агента»). Выход — заполненный `intent.md`.
   Каталог `intents/<INTENT-ID>/` отдельным шагом НЕ создаётся: он появляется
   при записи `intent.md` (Write). `mkdir` по этому пути guard запрещает — в
   папке артефактов разрешены только `*.md` и `meta.json`.
6. Агент вернул запрос на уточнение — задай вопросы пользователю через
   AskUserQuestion и перезапусти его с ответами (см. `_common.md`).
7. Валидация:
   `node "${CONVEYOR_ROOT}/core/scripts/validate-artifact.mjs" --file
   intents/<INTENT-ID>/intent.md --type intent`
   При `ok:false` — один возврат агенту со списком `missingSections`/
   `problems`, затем покажи пользователю остаток.
8. Сними рабочую область (`scope.mjs clear`). Покажи резюме intent'а,
   открытые вопросы и следующий шаг:
   `/conveyor:create-specification <INTENT-ID> <FE|BE|FE-BE> [номер]`.

## Ревью
Цикл ревью на этом этапе НЕ запускается (`_review-loop.md` не подключается):
качество проверяется валидацией шаблона и вопросами пользователю.

## Ошибки
- рабочая копия анализа не найдена → остановка с подсказкой склонировать её
  в путь из `settings.json` (плагин не клонирует);
- релевантных разделов в анализе не нашлось → это не ошибка: агент
  заполняет «Источники в анализе» пометкой «не найдено» и выносит вопрос в
  «Открытые вопросы».

## DoD
`intents/<INTENT-ID>/intent.md` создан и прошёл валидацию шаблона; рабочая
область снята; пользователю показаны открытые вопросы и следующий шаг.
