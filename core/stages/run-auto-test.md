# Этап /conveyor:run-auto-test — прогон автотестов в CI и отчёт

**Кто запускает:** тестировщик. **Агент:** не требуется — запуск сборки,
опрос статуса и отчёт о прогоне делает сам скилл (команда).
**Аргументы:** `TASK-ID`.
**Предусловие:** завершены этапы `implement-auto-test` и `implement-plan`
(`meta.json → stages['implement-auto-test'].done` и
`stages['implement-plan'].done` — оба `true`), в папке задачи лежит
`autotest-plan.md`, в meta.json записан `autotestBranch`.

Суть: прогнать уже написанные и запушенные автотесты задачи в Jenkins на
стенде и написать отчёт о прогоне — `report-auto-test.md`. Это ПЕРВЫЙ запуск
тестов задачи: `/conveyor:implement-auto-test` их только пишет, собирает и
ревьюит, поэтому и отчёт появляется здесь — раньше писать в него было нечего.
Автотесты пишутся параллельно с разработкой
(`/conveyor:implement-auto-test` ждёт только план автотестов), поэтому
проверка готовности реализации живёт ЗДЕСЬ: прогон на стенде без готовой
функциональности даёт красную сборку, которая ничего не говорит о качестве
ни тестов, ни продукта.

**Рабочая область:** чтение — рабочая копия автотестов (дифф ветки для
тегов, классы тестов); запись — только артефакты задачи
(`report-auto-test.md`, `meta.json`). В репозиторий автотестов этап не пишет
и не пушит: ветку пушит `/conveyor:implement-auto-test`. Кодовые базы FE/BE и
репозиторий анализа не открываются.

## Алгоритм
1. resolve-config (см. `_common.md`): нужна ссылка `autoTest`, её нет в
   `missingLinks`/`urlLinks` — иначе останови этап. Проверь предусловие по
   `docs/specs/tasks/<FE|BE>/<TASK-ID>/`: `stages['implement-auto-test'].done`,
   `stages['implement-plan'].done`, `autotest-plan.md`, `autotestBranch`.
   Не выполнено — остановка (см. «Ошибки»), рабочую область не ставь.
   Затем проверь, заведены ли кейсы в TMS:
   `node "<CONVEYOR_ROOT>/core/scripts/tms-cases.mjs" pending --task <папка задачи> --repo <копия автотестов>`
   (конфиг TMS для этого не нужен).
   Непустой `pending` — в плане или в коде (`pendingIn`) остались заглушки
   `PROJ-T999-N`: сборка пройдёт, но её результаты не свяжутся ни с одним
   кейсом в Zephyr. Это не блокер — спроси (AskUserQuestion): **сначала
   `/conveyor:update-tms`** (этап останавливается без рабочей области) /
   **прогнать так**.
2. Установи рабочую область:
   `scope.mjs set --stage run-auto-test --type <FE|BE> --task <TASK-ID>`
   (запись в репозитории запрещена — только артефакты задачи). Найди рабочую
   копию автотестов (`git-ops locate`).
3. **Функционал на стенде?** `implement-plan.done` значит «код в ветках», а
   не «развёрнуто на стенде». Спроси пользователя (AskUserQuestion):
   «Функционал задачи <TASK-ID> уже на стенде?» — варианты **да, на
   стенде** / **нет, ещё не развёрнут**. «Нет» — джобу не запускаем,
   причина «функционал ещё не на стенде» (см. «Ошибки»): прогон против
   старой версии стенда даст ложные падения.
4. **Можно ли запускать джобу.** Ссылка на неё —
   `settings.json → repos.autoTest.linkPipelineAutoTest`, в resolve-config это
   `links.autoTest.pipelineUrl`. Три проверки подряд, и каждая может закончить
   шаг причиной для отчёта (тогда сразу к шагу 6 — отчёт пишется и без
   сборки):
   1. ссылки нет в настройках → «джоба не настроена»;
   2. ветка запушена? —
      `node "<CONVEYOR_ROOT>/core/scripts/git-ops.mjs" pushed --path <копия> --branch <autotestBranch>`.
      Ответ `pushed: false` бывает двух видов, различай их по `checkFailed`
      (НЕ по тексту `reason`):
      - `checkFailed: false` — ветки нет в origin или локальная вершина
        впереди origin → «ветка не запушена»: джоба собирает ветку из
        origin, без push прогонится СТАРЫЙ код и отчитается зелёным. Сам
        этап не пушит — подскажи запушить ветку (или повторить шаг push
        `/conveyor:implement-auto-test`) и перезапустить этот этап;
      - `checkFailed: true` — проверку выполнить не удалось (нет сети, нет
        remote `origin`, битый клон), это НЕ незапушенная ветка. Пушить НЕ
        советуй — причина для отчёта «не удалось проверить ветку в origin:
        <reason и текст из warnings>», подскажи проверить доступ к origin и
        перезапустить этап;
   3. **инструменты.** Имён MCP-инструментов плагин не хранит: у каждой
      команды свой сервер Jenkins. ПОДБЕРИ их сам среди инструментов,
      доступных в этой сессии, — по имени сервера и описанию инструмента
      (Jenkins, CI, build) — и разложи по трём ролям: **запуск сборки с
      параметрами**, **статус сборки**, **результаты тестов сборки**.
      - роль закрыта одним подходящим инструментом — бери его;
      - кандидатов несколько и выбор неочевиден — спроси пользователя
        (AskUserQuestion), каким запускать;
      - инструмента на запуск сборки нет вовсе — джобу **не запускаем**:
        «нет MCP-инструментов для Jenkins». Через Bash (curl, jenkins-cli)
        сборку не запускай: так теряются и разрешение пользователя, и
        параметры джобы;
      - нет инструмента на результаты тестов — не блокер: в отчёт пойдут
        номер сборки, ссылка и статус, а статусы тестов и числа прогона —
        «нет данных».
   Прошли — спроси разрешение на запуск (AskUserQuestion), назвав джобу,
   ветку и то, чем будешь запускать. Отказ — тоже причина для отчёта.
5. **Теги и запуск.** Собери теги из тестов, которые изменила ветка: список
   файлов — `git-ops diff --path <копия> --base <mainBranch> --head <ветка>`
   (либо `git diff --name-only <mainBranch>...<ветка>`), из `*.java`/`*.kt`
   вытащи значения `@Tag("...")`. Покажи получившийся список пользователю и
   спроси: запускать по этим тегам или выбрать другие — список можно
   отредактировать (AskUserQuestion с множественным выбором и своим
   вариантом). В запуск идёт то, что подтвердил пользователь.
   Запусти сборку подобранным на шаге 4 инструментом: джоба — по ссылке из
   настроек, подтверждённые теги — в параметр `TAGS`. Прочие параметры
   джобы (в том числе `TEST_CYCLE`) не передавай: они остаются на умолчаниях
   джобы. Дальше опрашивай статус **раз в 3 минуты**, пока сборка не
   завершится, и забери результаты — по каждому тесту, если инструмент
   результатов это умеет. Сборка идёт дольше часа — спроси
   пользователя, ждать дальше или писать отчёт со статусом «в процессе».
6. **Отчёт о прогоне.** `report-auto-test.md` пишет СКИЛЛ, не агент — по
   каркасу `<CONVEYOR_ROOT>/core/templates/report-auto-test.md`, целиком и
   только по фактам: это подстановка фактов в каркас, и звать ради неё
   модель-агента незачем. Источников три: `autotest-plan.md`, `meta.json` и
   результаты сборки.
   - **Строки таблицы** — по таблице «Автотесты» плана: строка на каждую её
     строку, с ТЕМ ЖЕ ID, как он записан в плане сейчас. «Уровень» и «Вид» —
     из той же строки, «Файл теста» — её колонка «Класс», «Название» — из
     таблицы «Тест-кейсы» по ID.
   - **«Статус» строки** — по результатам сборки: `пройден` / `упал` /
     `пропущен`. Тест в результатах ищи по ID кейса, если инструмент его
     отдаёт; иначе — по классу из колонки «Класс» и методу, над которым в
     этом классе стоит `@TmsLink` с этим ID (рабочая копия автотестов).
     Не нашёл, инструмента результатов нет либо джобу не запускали —
     `нет данных`: не угадывай. `не реализован` — только когда строка плана
     осталась `[ ]` И теста нет в результатах сборки: тест, который прошёл
     или упал, реализован, что бы ни стояло в «Статусе» плана.
   - **«Комментарий»** — у упавшего теста ошибка из результатов сборки как
     есть, одной строкой; причину падения не классифицируй — разбор падений
     отдельная работа. У нереализованного — причина расхождения.
   - **«Расхождение с планом»** — из
     `meta.json → stages['implement-auto-test'].deviations` («ID теста →
     причина»); пусто или объекта нет — «нет». Ключ там мог остаться
     заглушкой `PROJ-T999-N`, которую `/conveyor:update-tms` уже заменил в
     плане: настоящий ключ — в `meta.json → tmsCases`. Тест сверх плана из
     `deviations` получает свою строку в таблице. Своих причин не сочиняй.
   - **«Итог прогона»** — «по плану» считай по таблице «Автотесты» плана,
     «реализовано» — строки отчёта без статуса `не реализован`, а
     «Пройдено / Упало / Пропущено / Нет
     данных» — по строкам таблицы отчёта, то есть только по тестам задачи.
     Числа всей сборки сюда не переносятся: она идёт по тегам и шире задачи.
   - **«Прогон в CI»** — ссылка на джобу (из настроек — всегда), ветка, теги,
     номер и ссылка на сборку, статус как вернул Jenkins, числа сборки.
     Джобу не запускали — в «Статус» идёт «джоба с автотестами не
     запускалась: <причина>», в «Теги» и «Сборку» — прочерк; ссылку на джобу
     и ветку всё равно пиши: по ссылке читатель откроет историю прогонов и
     тогда, когда этой сборки не было. Отказ от запуска отчёт НЕ отменяет:
     он пишется с причиной.
   - **«Ревью»** — из `meta.json → stages['implement-auto-test'].review`
     (`rounds`, `fixed`, `rebutted`, `unresolved`): цикл ревью шёл на этапе
     реализации, здесь его нет. Объекта нет — так и напиши, замечаний задним
     числом не придумывай.

   При ПОВТОРНОМ запуске (перезапуск упавшей сборки — обычный сценарий) отчёт
   переписывается целиком, без вопроса «перезаписать?» — он описывает
   ПОСЛЕДНИЙ прогон, история не копится.
   Так же переписывается отчёт прежней схемы — у задач, начатых до переноса
   отчёта на этот этап, его написал `/conveyor:implement-auto-test` ещё до
   прогона. У такой задачи в meta.json нет `deviations`: ДО перезаписи
   прочитай в старом отчёте строку «Расхождение с планом» и перенеси её в
   новый — другого источника этих причин нет.
   Затем сверь отчёт с планом:
   `node "<CONVEYOR_ROOT>/core/scripts/validate-artifact.mjs" --file <папка задачи>/report-auto-test.md --type report-auto-test --plan <папка задачи>/autotest-plan.md`
   — количество автотестов в отчёте обязано совпадать с планом.
   `planMismatch.missing` (строка плана потерялась) — `ok:false`: допиши
   строку и повтори. `planMismatch.extra` — допустим только тест сверх плана,
   названный в «Расхождении с планом». Непустой `placeholders` — в отчёте
   остался каркас шаблона: заполни и повтори. Этап не закрывай, пока
   проверка не зелёная.
7. Завершение этапа (см. `_common.md`): `validate-task-folder`, затем
   meta.json: `stages['run-auto-test'].done = true` и — рядом с
   `autotestBranch` — `autoTestJob`:
   `{ "url": "<ссылка на сборку>", "status": "<статус как вернул Jenkins: SUCCESS|UNSTABLE|FAILURE|ABORTED|… — либо «в процессе»>" }`.
   Джобу не запускали — `{ "url": null, "status": "не запускалась: <причина>" }`.
   Двух полей достаточно: остальное (джоба, ветка, теги, чем запускали)
   либо уже есть в meta.json, либо живёт в разделе «Прогон в CI» отчёта, и
   дублировать это в meta.json незачем. Поле относится к ПОСЛЕДНЕМУ прогону
   (перезапись, не накопление). Сними рабочую область (`scope.mjs clear`).

## Идемпотентность
Этап можно запускать повторно: после исправления тестов, после выкатки на
стенд, при перезапуске упавшей сборки. Повтор проходит все шаги заново
(включая вопрос про стенд) и перезаписывает `report-auto-test.md` и
`autoTestJob`. `stages['run-auto-test'].done` остаётся `true`.

## Ошибки
- `implement-auto-test` не завершён или `autotest-plan.md` нет →
  остановка: сначала `/conveyor:implement-auto-test <TASK-ID>`;
- этап `implement-plan` не завершён → остановка ДО установки рабочей
  области: тестам нечего проверять на стенде. Подскажи дождаться
  разработчиков. Содержимое `plan.md` при этом никуда не передаётся —
  предусловие о сроке, а не об источнике;
- функционал ещё не на стенде (ответ на шаге 3), ветка не запушена, ссылки
  на джобу нет, MCP-инструментов для Jenkins в сессии нет, сервер не
  отвечает, джоба недоступна, нет прав на запуск, пользователь отказал →
  этап НЕ падает: отчёт пишется с причиной в разделе «Прогон в CI» и
  статусами «нет данных», этап завершается. Запустить заново можно в любой
  момент;
- сборка упала (FAILURE/UNSTABLE) → это результат, а не ошибка этапа: статус
  и ссылка идут в отчёт, разбор падений — отдельная работа.

## DoD
`report-auto-test.md` написан по шаблону и сошёлся с планом по составу
автотестов (`validate-artifact --type report-auto-test --plan <autotest-plan.md>`:
`ok: true`, `planMismatch.missing` пуст, `extra` объяснён в «Расхождении с
планом»); у каждой строки — статус по результатам сборки либо «нет данных»;
в разделе «Прогон в CI» — либо номер, ссылка и статус
последней сборки (и теги, с которыми её запускали), либо причина, почему
джоба не запускалась; ссылка на джобу и ветка на месте; в meta.json записаны
`stages['run-auto-test'].done = true` и `autoTestJob` (ссылка и статус);
рабочая область снята. Конвейер задачи завершён.
