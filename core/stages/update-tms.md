# Этап /conveyor:update-tms — тест-кейсы в TMS (Zephyr Scale)

**Кто запускает:** тестировщик. **Агент:** не требуется — разбор плана,
вызовы MCP Jira и замену ID делает сам скилл (команда).
**Аргументы:** `TASK-ID`.
**Предусловие:** завершён этап `implement-auto-test`
(`meta.json → stages['implement-auto-test'].done = true`), в папке задачи
лежат `specification.md`, `autotest-plan.md` и `report-auto-test.md`, в meta.json записан
`autotestBranch`. Завершённость `implement-plan` НЕ проверяется: кейсы
описывают спецификацию, а не развёрнутую реализацию.

Суть: перенести таблицу «Тест-кейсы» плана автотестов в Zephyr Scale и
привести ID в порядок:
- **новый тест** (в плане заглушка `PROJ-T999-N`) — создать кейс в Zephyr;
- **существующий кейс** (в плане настоящий ключ `PROJ-T113`) — сверить с
  планом и поправить, если кейс расходится с ним по существу;
- заглушки заменить ключами созданных кейсов — в `autotest-plan.md`,
  `report-auto-test.md` и в `@TmsLink` кода автотестов. Пока в `@TmsLink`
  стоит заглушка, результаты сборки в Jenkins не свяжутся ни с одним кейсом
  в Zephyr — поэтому этап стоит ДО `/conveyor:run-auto-test`.

Таблицу разбирает скрипт `tms-cases.mjs`, а не модель: шаг, пересказанный
своими словами, — это уже другой кейс. Модель подбирает инструменты MCP,
сверяет существующие кейсы и общается с пользователем; полей кейса из
головы она не сочиняет — значения берёт из вывода `parse`.

**Рабочая область:** запись — артефакты задачи (`autotest-plan.md`,
`report-auto-test.md` — только замена ID; `meta.json`) и рабочая копия
автотестов. Guard различает только пути, не содержимое: запись в автотесты
на этапе открыта ЦЕЛИКОМ. Правит код только скрипт (`apply`, литерал в
`@TmsLink`), а перед коммитом `check-diff` проверяет, что в рабочей копии
изменены только строки `@TmsLink`, — это и есть ограничение, не слова в
промпте. Кодовые базы FE/BE и репозиторий анализа не открываются.

## Алгоритм
1. resolve-config (см. `_common.md`): нужна ссылка `autoTest`, её нет в
   `missingLinks`/`urlLinks` — иначе останови этап. Нужна и ссылка на
   тест-кейсы проекта — `settings.json → repos.autoTest.linkTMS`
   (`links.autoTest.tmsUrl`): по ней этап знает, в какую Jira и в какой
   проект заводить кейсы. Пусто — остановка «TMS не настроена: заполните
   repos.autoTest.linkTMS» (страница Test Cases проекта в Jira). Проверь предусловие по
   `docs/specs/tasks/<FE|BE>/<TASK-ID>/`: `stages['implement-auto-test'].done`,
   `specification.md`, `autotest-plan.md`, `report-auto-test.md`, `autotestBranch`. Не выполнено —
   остановка (см. «Ошибки»), рабочую область не ставь.
2. Установи рабочую область:
   `node "<CONVEYOR_ROOT>/core/scripts/scope.mjs" set --stage update-tms --type <FE|BE> --task <TASK-ID>`.
   Найди рабочую копию автотестов (`git-ops locate`) и проверь чистоту
   (`git-ops clean-check`): грязная копия → остановка — в коммит этапа
   попали бы чужие правки. Перейди в ветку задачи:
   `node "<CONVEYOR_ROOT>/core/scripts/git-ops.mjs" branch --path <копия> --branch <autotestBranch> --from <mainBranch>`.
3. **Разбор плана:**
   `node "<CONVEYOR_ROOT>/core/scripts/tms-cases.mjs" parse --task <абс. путь к папке задачи> --repo <копия автотестов>`.
   Названия полей Zephyr и их значения (префикс названия, приоритет и
   статус новых кейсов, «Вид тестирования», «Автоматизирован», «Уровень»,
   постоянные поля и поля по типу задачи) — конвенция КОМАНДЫ, а не
   плагина: скрипт берёт их из `.conveyor/tms.json` в репозитории
   автотестов. Файла нет или он заполнен с ошибками (`tmsConfig.errors`) —
   остановка: покажи пользователю образец
   `<CONVEYOR_ROOT>/core/templates/tms.example.json` и подскажи завести файл
   MR в репозиторий автотестов. Сам этап этот файл НЕ создаёт и не правит:
   значения полей знает команда, а не модель.
   `ok:false` с `problems` → остановка: план не разбирается, чинить его
   надо до выгрузки, а не подгонять кейсы. `warnings` покажи
   пользователю. Дальше работай с `cases[]`:
   - `kind: new` — заглушка без кейса: СОЗДАТЬ;
   - `kind: mapped` — кейс уже создан этим этапом (ключ в `tmsKey`), но
     заглушка ещё не заменена: прошлый запуск оборвался. Не создавать
     заново — сверить, как существующий, и заменить заглушку на шаге 9;
   - `kind: existing` — настоящий ключ: СВЕРИТЬ. `createdByConveyor: true`
     значит, что кейс завёл этот этап, и план для него — источник правды.
     `adopted: true` — кейс этап не создавал, а нашёл поиском и взял
     (шаг 8.1): это работа команды, сверяется как чужой.
   `testCase` каждого кейса — готовые значения полей (название с префиксом
   из конфига, цель, шаги с ожидаемым результатом, кастомные
   поля из конфига, связь с задачей). Цель — название, задача разработки и
   ТЕКСТЫ требований: REQ-ID из ячейки плана (одно или несколько через
   запятую) скрипт заменяет формулировками из таблицы «Функциональные
   требования» `specification.md` — сами REQ-ID в Zephyr не уходят, там их
   некому расшифровать. REQ-ID, которого нет в спецификации, — `problems`.
   Текст ячейки без ID (нефункциональные требования и критерии приёмки
   идут в спецификации списком без ID) уходит в цель как есть; пустая
   ячейка — только `warnings`. Цель — rich text Zephyr: строки уже
   разделены `<br>`, передавай `objective` как есть, не меняя `<br>` на
   переводы строк — они схлопнутся в пробел.
   Предусловия у кейса нет — его план не задаёт. `projectKey`
   (из ID тестов плана), `projectId` (из `linkTMS`, если в ссылке он есть) и
   `defaults` (приоритет, статус) — общие для новых кейсов. Поле со
   значением `null` не передаётся вовсе (значения плана нет в конфиге или
   приоритет/статус в нём не заданы — причина в `warnings`).
4. **Инструменты.** Имён MCP-инструментов плагин не хранит: у команды свой
   сервер Jira/Zephyr. ПОДБЕРИ их сам среди инструментов, доступных в этой
   сессии, — по имени сервера и описанию (Zephyr, Zephyr Scale, TM4J, test
   case, тест-кейс) — и разложи по ролям: **создание кейса**, **чтение кейса
   по ключу**, **правка кейса**, **поиск кейсов** (проект/папка/название),
   **шаги сценария** (если создание не принимает шаги), **связь кейса с
   задачей Jira**, **текущий пользователь**.
   Сервер выбирай тот, что смотрит в Jira из `linkTMS` (тот же хост).
   - роль закрыта одним подходящим инструментом — бери его; кандидатов
     несколько и выбор неочевиден — спроси пользователя (AskUserQuestion);
   - нет инструмента **создания**, а `new`-кейсы есть — остановка без единой
     записи: «нет MCP-инструментов для Zephyr» (подскажи подключить сервер,
     см. INSTALL.md);
   - нет **чтения** или **правки** — сверка существующих кейсов
     пропускается целиком, создание идёт; пропуск — в итоговую сводку;
   - через Bash (curl, REST API Jira) в Jira не ходи: так теряются и
     разрешение пользователя, и учётные данные сервера.
5. **Что спросить до работы** (одним AskUserQuestion, только если есть
   `new`-кейсы):
   - **владелец** (owner) новых кейсов — по умолчанию текущий пользователь
     Jira (роль «текущий пользователь»), его и предложи первым вариантом;
     инструмента нет — попроси ввести логин/ФИО. В settings.json владельца
     нет намеренно: файл общий на команду;
   - **папка** новых кейсов. Есть `existing`-кейсы и инструмент чтения —
     прочитай их и предложи их папки первыми вариантами (новые кейсы задачи
     обычно ложатся рядом со старыми); последний вариант — «другая папка»
     (свой ввод: путь от корня, например
     `/FE. РМ ОЦ/Задача Доверенность/Проверки полей authorityCreateDGR`).
     Существующих кейсов нет — только свой ввод. Папки в настройках нет
     намеренно: она меняется от задачи к задаче.
6. **Сверка существующих кейсов** (`existing` и `mapped`; инструменты чтения
   и правки есть). Прочитай кейс по `tmsKey` и сравни с `testCase`:
   - **поле автоматизации — только ПОВЫШАТЬ.** План знает, автоматизирует
     ли кейс ЭТА задача, но не знает, что регресс уже автоматизирован
     другой: «Автотест: нет» или `[ ]` в плане не значит «в Zephyr — Нет».
     У кейса есть `raiseOnly: { field, value }`, порядок значений — в
     `automatedRank.order` (слева направо: нет → в плане → написан).
     Меняй поле, только если значение кейса стоит ЛЕВЕЕ `value`; правее,
     равно или не из этого списка — не трогай;
   - **остальные служебные поля** — правь, если расходятся: постоянные
     поля (`constantFields`) и поля по типу задачи (`fieldsByTaskType`),
     поле уровня (`fields.level`), если в кейсе оно пустое; связь с задачей
     `<TASK-ID>`, если её нет. Названия полей — из
     `testCase.customFields`, а не по памяти;
   - **содержание** (название, цель, шаги, ожидаемые
     результаты, поле вида тестирования `fields.kind`):
     - кейс завёл этот этап (`createdByConveyor: true`) — план источник
       правды: любое расхождение правится по плану;
     - кейс писали тестировщики (в том числе взятый поиском — `adopted`) —
       правь ТОЛЬКО то, что противоречит плану
       по существу: по спецификации изменилось поведение (другой код
       ответа, другой текст ошибки, новый обязательный шаг, проверка
       больше не актуальна). Расхождение в формулировке, порядке слов,
       детализации — НЕ повод: кейс команды не переписывается под стиль
       плана. Такую правку предлагай точечно — замени нужный шаг или
       ожидание, остальные шаги оставь как есть;
   - **никогда** у существующего кейса не меняй владельца, папку, статус,
     приоритет, метки и префикс в названии — это решения команды;
   - кейс по ключу не найден (удалён, другой проект) — не заводи замену
     молча: в сводку «кейс <ключ> не найден в TMS», решение — за
     пользователем на шаге 7.
   По каждому кейсу собери список правок «поле: было → станет» (коротко,
   по шагам — номер шага и что меняется) и причину для содержательной
   правки чужого кейса.
7. **Предпросмотр и разрешение.** Создание и правка кейсов видны всей
   команде — без явного «да» ничего не пишется. Покажи одну сводку:
   - **создать** — заглушка, название, папка, число шагов, «Автоматизирован»;
   - **обновить** — ключ, правки и причина;
   - **без изменений / пропущено** — ключ и почему.
   Спроси (AskUserQuestion): **выполнить всё** / **только создать новые** /
   **выбрать** (множественный выбор по кейсам) / **отмена**. Отмена —
   сними область, этап завершается без записи в Zephyr и без `done`.
8. **Создание — по одному кейсу:**
   1. есть поиск — найди в проекте кейсы, в названии которых есть
      `testCase.title` (название БЕЗ префикса из конфига: префикс бывает
      меткой статуса, которую команда меняет руками, и по полному названию
      дубль не найдётся). Нашёлся — спроси: **взять найденный** /
      **создать новый всё равно**. Взятый записывается с флагом
      `--adopted` (шаг 8.3) — этап его не создавал, и своим он не
      становится: сверяется как чужой;
   2. создай кейс: `projectKey`, `testCase.name`, `objective`,
      папка и владелец (шаг 5), `defaults.priority`,
      `defaults.status`, кастомные поля из
      `testCase.customFields` (без `null`), шаги сценария по шагам —
      `description` / `testData` / `expectedResult`, связь с `<TASK-ID>`
      (`testCase.issueLinks`). Шаги создание не принимает — добавь их
      инструментом «шаги сценария»; его нет — шаги идут текстовым сценарием
      (`1) действие — ожидание`) и это отмечается в сводке;
   3. СРАЗУ после успешного ответа запиши ключ:
      `node "<CONVEYOR_ROOT>/core/scripts/tms-cases.mjs" record --task <папка задачи> --id <заглушка> --key <ключ>`
      (кейс взят на шаге 8.1 — добавь `--adopted`).
      Запись не удалась — прекрати создание: кейс без учёта будет создан
      повторно при следующем запуске. Причину — пользователю;
   4. сервер отверг значение кастомного поля (нет такой опции) — повтори
      ОДИН раз без этого поля и отметь в сводке; любая другая ошибка —
      кейс пропускается с причиной, остальные создаются. Значения полей
      вслепую не перебирай.
9. **Правки** одобренных кейсов — по одному; ошибка одного кейса не
   останавливает остальные, причина — в сводку.
10. **Замена заглушек:**
    `node "<CONVEYOR_ROOT>/core/scripts/tms-cases.mjs" apply --task <папка задачи> --repo <копия автотестов>`.
    Скрипт сначала проверяет, что рабочая копия найдена, — до любой записи:
    иначе план и отчёт были бы уже с ключами, а код ещё с заглушками. Потом
    меняет заглушки на ключи из `meta.json → tmsCases` в плане, отчёте и в
    `@TmsLink` кода (только литерал аннотации), сам проверяя рабочую
    область. `ok:false` — рабочая копия не найдена или запись не прошла
    guard (`denied`): остановка с причиной. `leftovers`:
    - `autotest-plan.md` / `report-auto-test.md` — заглушки, которым ключ
      не выдан (кейс пропущен или не создан);
    - `repo` — заглушки ЭТОЙ задачи, оставшиеся в коде вне `@TmsLink`
      (константа `@TmsLink(Ids.X)`, комментарий). Скрипт их не меняет:
      покажи пользователю — заменить их нужно руками, иначе прогон не
      свяжется с кейсом;
    - `foreign` — заглушки ЧУЖИХ задач (пришли из основной ветки): только
      предупреждение, этап ими не блокируется.
    Затем проверь артефакты — замена не должна их сломать:
    `node "<CONVEYOR_ROOT>/core/scripts/validate-artifact.mjs" --file <папка задачи>/report-auto-test.md --type report-auto-test --plan <папка задачи>/autotest-plan.md`
    (`planMismatch` обязан остаться пустым).
11. **Коммит.** Сначала проверь, что в рабочей копии изменены ТОЛЬКО строки
    `@TmsLink`:
    `node "<CONVEYOR_ROOT>/core/scripts/tms-cases.mjs" check-diff --task <папка задачи> --repo <копия автотестов>`.
    `ok:false` (`violations`: новый файл, удаление, строка без `@TmsLink`)
    — остановка БЕЗ коммита: покажи нарушения пользователю. Рабочая копия
    была чистой на шаге 2, значит, это правка, сделанная на этом этапе мимо
    скрипта. `repoFiles` из ответа `apply` непуст — закоммить РОВНО эти
    файлы в ветку автотестов (`git add -- <файлы>`, не `git add -A`)
    сообщением `ref: <TASK-ID> ключи кейсов TMS в @TmsLink`. Затем спроси
    (AskUserQuestion), что делать с push: **запушить сейчас** (пушит
    скилл) / **пользователь запушит сам** / **не пушить**. Без push
    `/conveyor:run-auto-test` прогонит старые заглушки — он это и проверит
    (`git-ops pushed`).
12. **Завершение** (см. `_common.md`): `validate-task-folder`; в meta.json —
    `stages['update-tms'] = { done, created: [ключи], updated: [ключи] }`.
    `done: true` — когда у задачи не осталось заглушек ни в плане, ни в
    коде: `node "<CONVEYOR_ROOT>/core/scripts/tms-cases.mjs" pending --task <папка задачи> --repo <копия автотестов>`
    вернул пустой `pending` (где остались — `pendingIn`). Иначе
    `done: false`, и сводка называет, что осталось. `foreignPlaceholders`
    (заглушки чужих задач) на `done` не влияют — только в сводку.
    `tmsCases` уже записан шагом 8. Сними рабочую область
    (`scope.mjs clear`). Напечатай сводку: создано (заглушка → ключ),
    обновлено (ключ: что), пропущено (почему). Следующий шаг —
    `/conveyor:run-auto-test`, когда завершён `implement-plan` и функционал
    развёрнут на стенде.

## Идемпотентность
Этап можно запускать повторно — после правки плана, после обрыва, после
добавления кейсов. Повтор создаёт только то, чего нет в `tmsCases`
(`kind: new`), созданные прошлыми запусками кейсы сверяет как свои
(`createdByConveyor`), взятые — как чужие (`adopted`, список
`meta.json → tmsAdopted`), и снова применяет замену — на заменённых ID она
ничего не меняет. Дублей не бывает по двум причинам: ключ пишется в
meta.json сразу после создания, а перед созданием идёт поиск по названию
без префикса.

## Ошибки
- пустая `repos.autoTest.linkTMS` → остановка до рабочей области: TMS
  не настроена;
- в репозитории автотестов нет `.conveyor/tms.json` или он с ошибками →
  остановка с образцом: конвенции полей заводит команда своим MR;
- `implement-auto-test` не завершён, нет `autotest-plan.md` или
  `report-auto-test.md` → остановка до рабочей области: сначала
  `/conveyor:implement-auto-test <TASK-ID>`;
- нет `specification.md` или в ней нет таблицы «Функциональные
  требования» → остановка: тексты требований для цели кейса брать неоткуда;
- `parse` вернул `ok:false` → остановка: план нужно починить (ячейки,
  колонки, ID, REQ-ID, которых нет в спецификации), выгружать сломанную
  таблицу нельзя;
- нет MCP-инструмента создания кейса при `new`-кейсах → остановка без
  записи; нет чтения/правки → сверка пропускается, создание идёт;
- рабочая копия автотестов грязная → остановка: коммит этапа не должен
  захватить чужие правки;
- Zephyr отверг кейс → кейс пропускается с причиной, остальные идут; этап
  завершается с `done: false`, повтор доделает;
- `record` не записал ключ → создание прекращается (иначе дубль при
  повторе);
- рабочая копия автотестов не найдена на `apply` → остановка до записи:
  артефакты не трогаются;
- `check-diff` нашёл правку не в `@TmsLink` → остановка без коммита;
- после `apply` в коде остались свои заглушки (`leftovers.repo`) → этап
  завершается с `done: false`, заглушки заменяются руками, затем повтор.
